# S40 — Order dedupe at "QuickBite"

**Concept:** `JSON.stringify()` serializes fields in the exact order they were written into the object (insertion order) — not alphabetically, not canonically. Two objects with identical fields and values, written in a different order, produce **two different strings**. This is a direct gap in earlier advice ("compare objects via `JSON.stringify()`, since `===` on objects always lies") — that advice only holds when both payloads have identical field order, which isn't guaranteed across clients or API versions.

## Snippet 1 — same order from two different clients

```js
const zamowienieWeb = { danie: "Pizza", ilosc: 2 };
const zamowienieApp = { ilosc: 2, danie: "Pizza" };

console.log(zamowienieWeb === zamowienieApp);
console.log(JSON.stringify(zamowienieWeb) === JSON.stringify(zamowienieApp));
console.log(JSON.stringify(zamowienieWeb));
console.log(JSON.stringify(zamowienieApp));
```

## Snippet 2 — dedupe function, original uses JSON.stringify()

```js
function czyDuplikat(historia, nowe) {
  const klucz = JSON.stringify(nowe);
  return historia.some(z => JSON.stringify(z) === klucz);
}

function czyDuplikatFix(historia, nowe) {
  return historia.some(z => z.danie === nowe.danie && z.ilosc === nowe.ilosc);
}

const historiaZamowien = [{ danie: "Pizza", ilosc: 2 }];
const noweZPolaAppki = { ilosc: 2, danie: "Pizza" };

console.log(czyDuplikat(historiaZamowien, noweZPolaAppki));
console.log(czyDuplikatFix(historiaZamowien, noweZPolaAppki));
```

**Predict before you scroll.**

## Verified (node, run before publishing)

```

```

Line by line: `zamowienieWeb === zamowienieApp` → `false` (two different objects, reference equality). `JSON.stringify(a) === JSON.stringify(b)` → `false`, even though both objects hold the same fields and values — because `JSON.stringify()` doesn't sort keys, it just walks them in insertion order. The two stringified outputs prove it side by side. Then the bug: `czyDuplikat`, which builds its dedupe key from `JSON.stringify()`, fails to recognize a logically identical order that arrived with fields in a different order — the kitchen would get two tickets for one order. Comparing fields individually (`czyDuplikatFix`) fixes it.

## Quiz

1. Why does `JSON.stringify({danie:"Pizza",ilosc:2}) === JSON.stringify({ilosc:2,danie:"Pizza"})` return `false` when both objects have identical fields and values?
   **Key:** `JSON.stringify()` serializes fields in insertion order, not any canonical order — different field order produces a different string despite identical content.
2. A dedupe system builds its key via `JSON.stringify(order)`. What exact change makes it reliable regardless of which client sent the payload?
   **Key:** Compare fields individually (`a.field === b.field` for each field) or normalize key order before serializing, instead of relying on the whole string.
3. Does `JSON.stringify()` sort object keys before serializing? Where does the key order in the output string actually come from?
   **Key:** No, it doesn't sort. The order in the output is simply the order in which the fields were written into (inserted into) the object.

## Card (spaced repetition)

**Front:** Why can two logically identical objects produce two different `JSON.stringify()` results?
**Back:** `JSON.stringify()` serializes fields in the order they were written into the object (insertion order), not alphabetically or canonically. `{danie:"Pizza",ilosc:2}` and `{ilosc:2,danie:"Pizza"}` have the same fields and values but produce different strings, so `JSON.stringify(a) === JSON.stringify(b)` → `false`. This is a gap in the common advice "compare objects via JSON.stringify()" — it only works when both payloads have identical field order, which isn't guaranteed across clients or API versions. Safer: compare fields individually, or normalize key order before serializing.
