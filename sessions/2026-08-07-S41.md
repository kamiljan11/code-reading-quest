# S41 — Object keys vs Map keys (2026-08-07)

**Concept:** operators & equality — plain object keys are always coerced to strings, `Map` keys keep their type (SameValueZero, no coercion).

**Story:** courier company "PakDrop" has a dedupe cache of already-seen parcels. Someone "modernised" it from a plain object to a `Map`. Nothing else changed. Dedupe quietly broke.

**Format:** order-of-execution — list the console lines in order.

## Snippet 1 — the old cache, plain object

```js
const widziane = {};
widziane[42] = "z weba";
widziane["42"] = "z appki";

console.log(Object.keys(widziane));
console.log(Object.keys(widziane).length);
console.log(widziane[42]);
console.log(42 === "42");
```

## Snippet 2 — same cache after the refactor to Map

```js
function przyjmij(cache, id, zrodlo) {
  if (cache.has(id)) {
    console.log(`ODRZUCONE (duplikat): ${id} z ${zrodlo}`);
    return;
  }
  cache.set(id, zrodlo);
  console.log(`PRZYJETE: ${id} z ${zrodlo}`);
}

const cache = new Map();
przyjmij(cache, 42, "web");
przyjmij(cache, "42", "appka");
przyjmij(cache, 42, "web-retry");
console.log("rozmiar cache:", cache.size);
```

## Verified

Run with `node` (v22.22.3):

```
=== Snippet 1 ===
[ '42' ]
1
z appki
false

=== Snippet 2 ===
PRZYJETE: 42 z web
PRZYJETE: 42 z appka
ODRZUCONE (duplikat): 42 z web-retry
rozmiar cache: 2
```

Reading of it: an object can only be keyed by strings (or symbols), so `widziane[42]` really is `widziane["42"]` — one key, second write overwrites the first. `Map` stores the key with its original type and compares with SameValueZero (the same algorithm `.includes()` uses), so the number `42` and the string `"42"` are two separate entries. The second call is the real business duplicate (same parcel, different app); the third is only a duplicate to the code. The log hides all of this, because a template literal prints number `42` and string `"42"` identically.

Fix: normalise the key type before every `has`/`set` — `const k = String(id)`.

## Quiz

1. Why do `widziane[42]` and `widziane["42"]` produce ONE key, while `cache.set(42, ...)` and `cache.set("42", ...)` produce a `Map` of size 2?
   **Key:** object keys are always coerced to strings, so both writes hit `"42"` and the second overwrites the first. `Map` compares keys with SameValueZero without any type conversion, so number and string are different keys.
2. The log shows `42` three times and never a quote. Why can't you see the bug from the log, and what would you change in `console.log` to expose the type?
   **Key:** a template literal calls `String(id)`, so number and string print identically. Use `console.log("id:", id)` without interpolation (node prints `'42'` with quotes for a string) or log `typeof id` explicitly.
3. The dedupe cache must work whether the id arrives from JSON as a number or a string. What single change fixes the `Map` version?
   **Key:** normalise the key type before every `has`/`set`, e.g. `const k = String(id)`.

## SM-2 card

**Front:** What is the difference between a key in a plain object `{}` and a key in a `Map`?

**Back:** An object key is always coerced to a string (`obj[42]` and `obj["42"]` are the same key — the second write overwrites the first, `Object.keys().length` is 1). A `Map` keeps the key's original type and compares with SameValueZero (the same algorithm as `.includes()`), so `42` and `"42"` are two separate entries and `map.size` is 2. Consequence: refactoring a dedupe cache from `{}` to `Map` silently breaks deduplication when the same id arrives sometimes as a number and sometimes as a string. The log won't show it, because a template literal prints both identically. Fix: `String(id)` before `has`/`set`.

## Takeaway

A refactor that "only swaps the data structure" can change the answer to a business question — and the log looks the same in both versions. When reading someone else's diff, don't just ask what changed; ask which equality rule the change dragged in with it.
