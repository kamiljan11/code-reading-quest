# S46 — Chained comparisons: the gate that never rejected anyone

**Concept:** Operators and comparisons (JavaScript)
**Format:** find-bug
**Date:** 2026-08-12

## The idea

`140 <= height <= 180` is **not** a range check in JavaScript.

Relational operators (`<`, `>`, `<=`, `>=`) are **left-associative**, so the engine reads
`(140 <= height) <= 180`. The first pair produces a **boolean**, and the second comparison
coerces that boolean to a number: `false` becomes `0`, `true` becomes `1`. Both `0 <= 180`
and `1 <= 180` are true, so the whole condition is **always true** and the `else` branch is
dead code. No error, no warning — the line looks like school maths and sails through review.

The mirror image is just as bad: `180 >= x >= 140` is **always false**, because `0 >= 140`
and `1 >= 140` are both false. Same mistake, opposite outcome.

## Scenario

Go-kart track "Track Zero". The gate is supposed to admit drivers between 140 and 180 cm.
There is also an age guard. One of the two guards lies.

## Snippet 1 — four chains, dry

```js
console.log(3 < 2 < 1);
console.log(1 < 2 < 3);
console.log(140 <= 175 <= 180);
console.log(140 <= 200 <= 180);
console.log(true + 1);
```

## Snippet 2 — the gate

```js
function wpuscNaTor(imie, wzrost, wiek) {
  if (wiek < 8) {
    console.log("ODMOWA " + imie + ": za maly wiek (" + wiek + ")");
    return;
  }
  if (140 <= wzrost <= 180) {
    console.log("OK " + imie + " (" + wzrost + " cm)");
  } else {
    console.log("ODMOWA " + imie + ": wzrost poza zakresem (" + wzrost + " cm)");
  }
}

wpuscNaTor("Ola", 165, 24);
wpuscNaTor("Bartek", 132, 11);
wpuscNaTor("Cela", 194, 31);
wpuscNaTor("Dawid", 170, 6);
wpuscNaTor("Ewa", 0, 40);
```

## Verified

Run with `node v22.22.3`.

Snippet 1:

```
true
true
true
true
2
```

Snippet 2:

```
OK Ola (165 cm)
OK Bartek (132 cm)
OK Cela (194 cm)
ODMOWA Dawid: za maly wiek (6)
OK Ewa (0 cm)
```

The height gate admitted **everyone** who cleared the age guard — including a driver
recorded as 0 cm tall. The only `ODMOWA` in the log comes from the age guard, which is
written correctly as a single full comparison.

Intermediate steps, run separately:

```
140 <= 132        -> false        false <= 180 -> true
140 <= 194        -> true         true  <= 180 -> true
Number(false)     -> 0            Number(true) -> 1
typeof (140<=132) -> "boolean"
```

Direction matters, run separately:

```
5 > 4 > 3         -> false
180 >= 200 >= 140 -> false
0 <= -5 <= 0      -> true
"b" < "c" < "a"   -> false        (true < "a" is 1 < NaN)
```

The fix, run separately (`140 <= x && x <= 180`):

```
165 -> true
132 -> false
194 -> false
0   -> false
```

## Quiz

**1. `140 <= X <= 180` is always true, but `180 >= X >= 140` is always false. Same intended range, both broken — where does the difference come from?**

Both evaluate the left pair first and collapse it to `0` or `1`. What happens next depends
on what that `0`/`1` is compared against. `"is 0/1 <= 180"` is true for both values, so the
first form is a tautology that admits everyone. `"is 0/1 >= 140"` is false for both, so the
second form rejects everyone — including `X = 175`, which is inside the intended range.

**2. Does `if (wzrost >= 140 && wzrost <= 180)` fix it completely? What does it do to `("Ewa", 0, 40)`, and why does that matter more than the Cela case?**

Yes — verified: true only for 165, false for 132, 194 and 0. Cela is a "too tall" bug, a
missed boundary someone would eventually notice at the track. A height of `0` means the
field was never filled in, or arrived empty from a form. The old condition waved
**missing data** through exactly as smoothly as valid data — it wasn't just failing to
enforce a range, it wasn't checking that anything was entered at all.

**3. The same associativity rule drove the S44 lesson about `+`. Name one thing `<` does differently in a three-value chain, and say which bug is harder to spot in a log.**

`+` carries its result forward **without losing content**: `"Score: " + 7 + 3` loses the
arithmetic, but the digits `7` and `3` are still visible, so the weird output (`73`) draws
attention to itself. `<` **collapses the intermediate value to a single bit**: after the
first comparison, `165` becomes `1` and `132` becomes `0`, and the original number ceases
to exist. The `<` bug is harder — its symptom isn't a strange output but the **absence** of
output you expected. A wrong value shouts; a branch that never ran says nothing.

## Card (SM-2)

**Front:** What does JS do with `140 <= x <= 180`?

**Back:** It reads it as `(140 <= x) <= 180`, because `<`, `>`, `<=`, `>=` are
left-associative (same rule as `+`). The first pair yields a boolean, coerced to a number in
the second comparison: `false` → `0`, `true` → `1`. So the real computation is `0 <= 180` or
`1 <= 180` — both true, condition always true, `else` is dead code. The reverse spelling
`180 >= x >= 140` is always false. Direction decides which way it breaks: `3 < 2 < 1` is
true, `5 > 4 > 3` is false. No error, no warning. The only correct range check is two full
comparisons joined with `&&`: `140 <= x && x <= 180`.

## Takeaway

A bug that produces no wrong output — only the absence of output you expected — survives
every happy-path test. On a client deployment that is the equivalent of a guard which has
never rejected a single record: nobody files a ticket, because nothing breaks loudly. When
reading someone else's condition, don't ask "does it let through what it should". Ask
**"is there any input at all that this condition would reject?"** If you can't invent one in
five seconds, it isn't a condition — it's decoration.
