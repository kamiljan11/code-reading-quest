# S47 — null passes the range check, then fails the equality check

**Concept:** operators and comparisons — relational operators vs `==` use two different rules for `null`
**Format:** predict the output
**Theme:** ❄️ "Permafrost" cold storage

## The setup

Permafrost cold storage keeps vaccines. Five sensors report battery level once an hour.
The panel has two jobs: reject any reading that is not a sensible percentage, and shout if
the battery has dropped to zero. The developer wrote the validation as "0 to 100 inclusive",
because `0%` is a legal, meaningful value. Overnight sensor C3 stopped responding and
returned `null`. In the morning the log looks calm.

## Round 1 — five dry comparisons

```js
console.log(null >= 0);
console.log(null > 0);
console.log(null == 0);
console.log(undefined >= 0);
console.log(null >= 0 && null <= 0);
```

## Round 2 — the panel

```js
function przyjmijOdczyt(czujnik, bateria) {
  if (bateria >= 0 && bateria <= 100) {
    if (bateria == 0) {
      console.log("KRYTYCZNA " + czujnik + ": bateria " + bateria + "%");
    } else {
      console.log("OK " + czujnik + ": bateria " + bateria + "%");
    }
  } else {
    console.log("BRAK DANYCH " + czujnik);
  }
}

przyjmijOdczyt("A1", 87);
przyjmijOdczyt("B2", 0);
przyjmijOdczyt("C3", null);
przyjmijOdczyt("D4", undefined);
przyjmijOdczyt("E5", "45");
```

Intermediate steps, run separately:

```
Number(null)        -> 0
Number(undefined)   -> NaN
null == undefined   -> true      null === undefined -> false
null <= 0           -> true      null < 1  -> true    null >= -1 -> true
null == false       -> false     null === null -> true   null === 0 -> false
undefined == 0      -> false     undefined > -1 -> false  undefined < 1 -> false
"45" >= 0           -> true      "45" == 0 -> false
""   >= 0           -> true      ""   == 0 -> true
typeof null         -> "object"
[] >= 0             -> true      [] == 0 -> true
```

Three candidate validations, run on `[87, 0, null, undefined, "45"]`:

```
(a) v >= 0 && v <= 100                        -> true true true  false true
(b) v != null && v >= 0 && v <= 100           -> true true false false true
(c) typeof v === "number" && v >= 0 && v <= 100 -> true true false false false
```

Swapping the inner guard to `===` (quiz 1), run separately: C3 -> `OK`, B2 -> `KRYTYCZNA`,
E5 -> `OK`. The log is character-for-character identical.

## Why

Relational operators (`<`, `>`, `<=`, `>=`) share one procedure: coerce both sides through
`Number()`, then compare numbers. `Number(null)` is `0`, so `null >= 0` really evaluates
`0 >= 0` and is `true`. `==` is a different operator with its own hand-written exception
table, in which `null` is deliberately **not** coerced to a number — it equals only
`undefined` and itself. So `null == 0` and `null === 0` are both `false`.

The consequence is a small paradox: `null >= 0 && null <= 0` is `true`, meaning `null`
"fits inside the interval [0, 0]" while not being equal to zero. `>=` is not a composition
of `>` and `==`; it never asks `==` for an opinion.

`undefined` goes the other way. `Number(undefined)` is `NaN`, and `NaN` loses every
relational comparison, so `undefined` is rejected by the same `if` that let `null` through.
Two markers of missing data, one branch, opposite fates.

## Quiz

1. **A colleague changes the guard to `if (bateria === 0)`. Does that fix C3?**
   No. Verified: the log is identical, because `null == 0` and `null === 0` are both `false`.
   The bug is in the *outer* `if` — the range check admitted `null` as a zero. The inner guard
   only faithfully reported that the value is not zero. Changing `==` to `===` treats the
   symptom on the wrong floor.

2. **`null == 0` is `false` but `null >= 0` is `true`. Where does the intuition break?**
   On the assumption that `>=` is `>` or `==`. It is not. `>` and `>=` belong to the relational
   family with a shared `Number()` coercion step; `==` is a separate operator with a manual
   exception table where `null` is a special case. Comparison operators in JS do not form one
   coherent logical system — they are a set of separate rules that have to be learned separately.

3. **Which of (a), (b), (c) rejects C3, and which also rejects E5?**
   (a) admits `null` — that is the bug. (b) rejects both `null` and `undefined` in one shot
   (`!= null` is the one place where loose equality is the idiom, not the mistake) but still
   admits `"45"`. (c) rejects `null`, `undefined` and `"45"`. For sensor data (c) is correct:
   a reading arrives as JSON over HTTP, where the field can be a number, a string, `null`, or
   absent — four possibilities, one of them valid. `typeof` asks the real question ("is this a
   measurement at all") before any comparison operator gets a chance to coerce anything. The
   ordering matters too: `typeof` goes first, and short-circuiting protects the rest.

## SM-2 card

**Front:** Why does `null >= 0` return `true` when `null == 0` returns `false`?

**Back:** Two different operator families. Relational (`<`, `>`, `<=`, `>=`) coerce both sides
through `Number()`; `Number(null)` is `0`, so it evaluates `0 >= 0` -> `true`. `==` has its own
exception table where `null` is not coerced and equals only `undefined` and itself, so
`null == 0` and `null === 0` are both `false`. Side effect: `null >= 0 && null <= 0` is `true`.
`>=` is not a composition of `>` and `==`. Practical impact: a `x >= 0 && x <= 100` validation
admits a missing reading as a valid zero, and a later `x == 0` guard will not catch it, because
the bug lives one floor up. `undefined` behaves oppositely — `Number(undefined)` is `NaN`, so
every relational comparison is `false` and it gets rejected. Reject both at once with
`x != null`; for API/sensor data prefer `typeof x === "number"`, which also rejects a smuggled
`"45"`.

## Takeaway

A validation that rejected something and alarmed on something else looks like it works. That is
the most expensive illusion in integration code: a log full of `OK` raises suspicion, a mixed log
suppresses it. When reading someone else's validation, do not ask "does it let good data through".
Ask: "what non-data does it let through while pretending it is data". Between someone else's API
and your `if` there are four different kinds of emptiness, and each one carries a different passport.
