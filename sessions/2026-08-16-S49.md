# S49 — Optional chaining short-circuits the whole chain, but guards only its own link

**Concept:** operators and comparisons · **Format:** what-if · **Language:** JavaScript

`?.` does two things at once, and reading code you usually notice only the first one.
It **short-circuits the entire rest of the chain** when the value on its left is `null`
or `undefined` — so `a?.b.c.d` does not throw on an empty `a`, despite the plain dots
after it, because those links never execute. But it **guards only its own link** — with
a present `a` and an empty `b`, the same line throws. The result of a short-circuit is
always `undefined`, never `null`.

## Story

Night shift at the "Orbita" helpdesk. Tickets arrive from a partner API and every one
has a different shape: companies have an account manager, private customers have
`klient.firma = null`, old records have no `firma` field at all, and the oldest have no
`klient` either. The developer was told at code review "add optional chaining, then
there will be no exceptions", and added it. In the morning the panel shows five calm
lines and the manager asks why nobody was notified.

## Round 1 — four payload shapes

```js
const zg1 = { id: "A-1", klient: null };
const zg2 = { id: "A-2", klient: { firma: undefined, priorytet: null } };
const zg3 = { id: "A-3", klient: { priorytet: "krytyczny", firma: { nazwa: "Nordkraft", opiekun: null } } };
const zg4 = { id: "A-4" };

console.log(zg1.klient?.firma, zg2.klient?.firma?.nazwa);
console.log(zg1.klient?.firma.nazwa.toUpperCase());
console.log(typeof zg2.klient?.firma?.nazwa, zg3.klient?.firma?.opiekun?.mail);
console.log("Firma: " + zg2.klient?.firma?.nazwa);
console.log(zg3.klient?.firma?.nazwa?.length, zg1.klient?.firma?.nazwa?.length);
```

## Round 2 — the panel and the escalation

```js
function podsumuj(zg) {
  const nazwa = zg.klient?.firma?.nazwa;
  const opiekun = zg.klient?.firma?.opiekun;
  const priorytet = zg.klient?.priorytet ?? "normalny";
  const skrot = nazwa?.slice(0, 4) ?? "???";
  console.log(zg.id + " | " + nazwa + " | " + skrot + " | prio " + priorytet + " | mail " + opiekun?.mail);
}

function eskaluj(zg) {
  try {
    console.log(zg.id + " -> " + zg.klient?.firma.opiekun.mail);
  } catch (e) {
    console.log(zg.id + " -> WYJATEK: " + e.message);
  }
}

[zg1, zg2, zg3, zg4].forEach(podsumuj);
[zg1, zg2, zg3, zg4].forEach(eskaluj);
```

## Question

a) Round 1: write out the five lines. Next to line two, explain why `.nazwa.toUpperCase()`
on emptiness does not blow up, given there are still two plain dots after the `?.`.

b) Round 2: write out both logs. Then the main question of the day — a colleague reads
the two exceptions and "fixes" `eskaluj` by adding `?.` at **every** link:
`zg.klient?.firma?.opiekun?.mail`. Write the log after that change, point out exactly
which lines changed, and say whether tickets A-2 and A-3 now get handled.

c) Which ticket is actually the most dangerous, and why is the "fixed" version worse for
the person on duty than the one that threw exceptions?

**Hint (direction, not answer):** don't read the chain as a whole. Break it into links
and write down, for each link separately, what the value on its left is and whether that
junction has a question mark or a plain dot. Then walk left to right and stop at the
first place where emptiness meets a plain dot.

## Quiz

**1.** In `podsumuj`, the line `const priorytet = zg.klient?.priorytet ?? "normalny";`
works for all four tickets, even though A-2 has an explicit `priorytet: null` and A-1 has
no `klient` at all. Which part of the line saves which case? Why would `?.` alone not be
enough, and why would `??` alone throw?

> `?.` guards the **path in**, `??` guards the **value at the end**. Verified:
> `zg2.klient?.priorytet` gives `null` — `?.` passes `null` through untouched — and only
> `?? "normalny"` turns it into a sensible default. Without `?.`:
> `zg1.klient.priorytet ?? "normalny"` with `klient = null` throws
> `TypeError: Cannot read properties of null (reading 'priorytet')`, because `??` acts on
> the **result**, and you have to reach the result first. Same pairing as S48 seen from
> the other side: there `=` caught `undefined` and let `null` through; here `?.` catches
> both emptiness markers on the way in, but has no opinion about the value it arrives at.

**2.** `?.` returns `undefined` even when the short-circuit was triggered by `null`. Where
in today's code does that lost information matter — where can the person on duty not tell
"this company has no account manager" from "this customer does not exist"?

> `opiekun?.mail` in `podsumuj`: all four tickets print `mail undefined`, for entirely
> different reasons. A-3 has a company and full data, it simply has nobody assigned
> (`opiekun: null` = "we know there is nobody"), while A-1 and A-4 have no customer at all
> ("we know nothing"). Those are two different operational decisions: assign a manager
> versus fix the record. Distinguishing them requires asking about each stage separately,
> e.g. `zg.klient == null ? "NO CUSTOMER" : zg.klient.firma == null ? "PRIVATE PERSON"
> : zg.klient.firma.opiekun == null ? "COMPANY, NO MANAGER" : zg.klient.firma.opiekun.mail`.
> Note the `== null` — the one justified use of loose equality in JS, catching `null` and
> `undefined` in a single check.

**3.** Four spellings: (a) `zg.klient?.firma?.opiekun?.mail`, (b) `zg.klient?.firma?.opiekun.mail`,
(c) `zg?.klient?.firma?.opiekun?.mail`, (d) `zg.klient.firma?.opiekun?.mail`. Which behaves
differently at `zg = {klient:{firma:undefined}}`? What about at `zg = {klient:null}`? And
which is the only one that survives `zg === undefined`?

> Verified. At `{klient:{firma:undefined}}` **all four** return `undefined` — no difference
> at all. The emptiness sits at `firma`, and the `?.` placed at `firma` short-circuits
> everything after it, so the plain dot in (b) is never reached; in (d) you get to `firma`
> without trouble because `klient` exists, and the short-circuit catches there too. That is
> the whole point of the day: **a plain dot after a short-circuit is harmless, because it
> never runs.** At `{klient:null}` the difference appears: a/b/c give `undefined`, while (d)
> throws `Cannot read properties of null (reading 'firma')` — it is the only one without a
> `?.` at the first junction, which is exactly where the emptiness is. At `zg === undefined`
> the only survivor is (c), the only one with `?.` at the root. Rule: what matters is solely
> whether the question mark sits at **the junction where the emptiness actually is**; every
> other `?.` in the chain is decoration at that moment.

## Card (spaced repetition)

**Front:** What exactly does `?.` do in the chain `a?.b.c.d` — and what does it *not* protect against?

**Back:** Two things at once. **(1) Short-circuit:** when the value on the left of `?.` is
`null` or `undefined`, the entire rest of the chain does not run and the result is
`undefined` — verified: `zg.klient?.firma.nazwa.toUpperCase()` with `klient === null` does
not throw despite three plain dots after the `?.`, because they never execute. A plain dot
after a short-circuit is harmless. **(2) Scope of protection:** `?.` checks only its own
junction — the same line with `klient = {firma: undefined}` throws
`TypeError: Cannot read properties of undefined (reading 'opiekun')`. What matters is only
whether the question mark sits at the junction where the emptiness actually is. The result
of a short-circuit is **always `undefined`, never `null`** — the information about which
kind of emptiness it was is lost, so the log cannot tell "company with no manager" from
"no such customer". `?.` does not protect against a **bad value**, only against emptiness:
`0?.toFixed(1)` -> `"0.0"`, `""?.length` -> `0`, and `fn?.()` with `fn = 5` still throws
`TypeError: fn is not a function`. The professional trap: sprinkling `?.` on every link
silences **all** exceptions (verified: four quiet `undefined`s) and does not remove the
problem, it only moves the moment of the blast — `"mail " + undefined` -> `"mail undefined"`,
`undefined + 1` -> `NaN`, `JSON.stringify({a: undefined})` -> `{}`. Division of labour:
`?.` guards the path in, `??` guards the value at the end.

## Takeaway

An exception is code asking for help. `undefined` is code reporting success and moving on.
Sprinkling `?.` over every link fixes nothing — it mutes. In integration work the most
expensive failures do not look like failures: a critical ticket and an empty ticket print
an identical line. Reading someone else's chain, don't ask "will this blow up". Ask: where
does the `undefined` land if it doesn't.
