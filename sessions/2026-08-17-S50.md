# S50 — `typeof` on an undeclared variable (2026-08-17)

**Concept:** `typeof` is the only place in JavaScript where you may touch a name that was never declared and not get a `ReferenceError` — you get the quiet string `"undefined"` instead. That protection covers the bare identifier and nothing else.

**Story — database migration "Feniks", 23:40.** The migration script rewrites tables into a new schema. There is exactly one safeguard: a global config sets `tryb: "suchy-bieg"` (dry run, no writes). The guard checks for that config with `typeof`, "because that way it won't blow up if the config is missing". By morning both tables are migrated. In production. The log has four calm lines and not one word that looks like an error.

## Round 1 — what `typeof` says about five different things

```js
var trybSuchy = null;
const limit = 0;

console.log(typeof trybSuchy, typeof limit);
console.log(typeof nieMaTakiejZmiennej, typeof NaN);
console.log(typeof [], typeof {}, typeof console.log);
console.log(typeof "12" === "number", typeof (12 + ""));
console.log(typeof typeof nieMaTakiejZmiennej);
```

## Round 2 — two versions of the same guard, the same typo in both

```js
globalThis.konfigMigracji = { tryb: "suchy-bieg", limit: 500 };

function migruj(tabela) {
  if (typeof konfigMigracj !== "undefined") {
    console.log(tabela + ": tryb " + konfigMigracji.tryb + ", limit " + konfigMigracji.limit);
  } else {
    console.log(tabela + ": BRAK KONFIGU -> tryb domyslny (zapis na produkcji)");
  }
}

function migrujTwardo(tabela) {
  try {
    if (konfigMigracj) {
      console.log(tabela + ": tryb " + konfigMigracji.tryb);
    } else {
      console.log(tabela + ": BRAK KONFIGU");
    }
  } catch (e) {
    console.log(tabela + ": " + e.name + " -> " + e.message);
  }
}

function sprawdzLicznik() {
  try {
    console.log("licznik -> " + typeof licznik);
  } catch (e) {
    console.log("licznik -> " + e.name + ": " + e.message);
  }
  let licznik = 0;
}

migruj("klienci");
migruj("faktury");
migrujTwardo("klienci");
sprawdzLicznik();
console.log(typeof konfigMigracji, typeof konfigMigracj);
```

The line that lies is `console.log(tabela + ": BRAK KONFIGU -> tryb domyslny (zapis na produkcji)")`. The config exists and says "dry run"; the log reports it missing. The safeguard added "so it wouldn't blow up" is the cause of the incident — the version without `typeof` fails loudly on the first table, before anything is written.

## Quiz

**1. Which of the four guards makes the typo surface immediately while a genuinely missing config still does not kill the script: (a) `typeof konfigMigracj !== "undefined"`, (b) `globalThis.konfigMigracj !== undefined`, (c) `"konfigMigracj" in globalThis`, (d) `konfigMigracj !== undefined`?**

None of the three "safe" ones. Verified: against the typo they return `false / false / false`, and only (d) throws `ReferenceError: konfi is not defined`. Every guard built on emptiness treats "typo" and "missing" as the same case, because to the engine both mean "no such name". Only (c) `in` distinguishes "never declared" from "declared and set to `undefined`" — it looks at the key, `typeof` looks at the value.

**2. `typeof konfi` returns `"undefined"`, but `typeof konfi.tryb` throws. Why does adding `.tryb` remove the whole protection?**

Because `typeof` protects the bare identifier only. `typeof konfi.tryb` is an ordinary property read: the engine has to find `konfi` before it can reach `.tryb`, and it fails on that first step. Same shape as optional chaining from S49 — one specific position is protected, everything past it is a normal read. `typeof globalThis.konfi` survives, because `globalThis` always exists and a missing *property* is just `undefined`, not an error. Practical consequence: keep flags as fields of one object instead of bare global names, and you never need `typeof` at all.

**3. Three popular claims about `typeof`, all false — give a counterexample to each.**

(a) "`typeof` never throws" — in the temporal dead zone it does: `typeof licznik` before `let licznik = 0` in the same scope throws `ReferenceError: Cannot access 'licznik' before initialization` (with `var` it would be a quiet `"undefined"`). (b) "`typeof x === 'object'` means object" — `typeof null` is `"object"` and `typeof []` is `"object"` (use `Array.isArray()`), so the test lets through the exact value it was meant to block. (c) "`typeof x === 'number'` means you can do arithmetic" — `typeof NaN` is `"number"`. In integration code (b) is the dangerous one: payload validation usually asks "is this an object", and that question answers `true` for `null`.

## Card

**Front:** What does `typeof` do with a variable that was never declared — and where does that protection end?

**Back:** It returns the string `"undefined"` instead of throwing (verified: bare `brakZmiennej` throws `ReferenceError`, `typeof brakZmiennej` returns `"undefined"`). It is the only such place in JS. Consequence: a typo in a flag name inside `typeof flaga !== "undefined"` does not blow up, it quietly selects the "no config" branch. The protection covers the bare identifier only — `typeof konfi.tryb` throws, because reaching `.tryb` requires finding `konfi` first (same shape as `?.` in S49). `typeof globalThis.konfi` does not throw, because `globalThis` exists. "typeof never throws" is a myth: the TDZ of `let`/`const` throws `Cannot access 'x' before initialization`. `typeof` cannot tell "never declared" from "declared as `undefined`" — `in` can. Glossary: `typeof null` -> `"object"`, `typeof NaN` -> `"number"`, `typeof []` -> `"object"`, `typeof fn` -> `"function"`, `typeof typeof x` -> `"string"`.

## Takeaway

A safeguard that differs from having no safeguard only in that it does not shout is not a safeguard. In integration work a typo in a flag name and a missing flag are the same case to the engine — and the difference between a dry run and an overwritten production database to the client.
