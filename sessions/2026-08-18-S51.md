# S51 — parseInt vs Number: the parser that stops reading and never tells you

**Date:** 2026-08-18 · **Concept:** operators & conversions · **Format:** order-of-execution

## The scene — weighbridge "Tonaz"

06:10, weighbridge at the entrance to a construction site. A truck pulls onto the plate,
the operator copies four masses from handwritten dockets into the terminal and hits ENTER.
The terminal sums them, compares against a 2500 kg limit and raises the barrier or doesn't.

The dockets are handwritten, so one has a unit, one has a comma instead of a dot,
and one came from a spreadsheet in exponential notation.

The barrier goes up. The real load is 3012.5 kg.

## Concept

`parseInt` does not convert a string to a number. It **reads it from the left** and stops at
the first character it does not understand, returning whatever it managed to read — with no
signal that anything was left behind.

`Number()` works on the whole thing: either the entire string is a valid number, or `NaN`.

## Round 1 — five inputs through both tools

```js
const wpisy = ["80kg", "12,5", "1e3", "", "0x1F"];

for (const w of wpisy) {
  console.log(`"${w}" -> parseInt: ${parseInt(w)} | Number: ${Number(w)}`);
}
```

## Round 2 — the same terminal, three ways to count the same load

```js
const LIMIT = 2500;
const terminal = ["1200", "12,5", "1e3", "800kg"];

let suma = 0;
for (const wpis of terminal) {
  suma += parseInt(wpis);
}
console.log("suma parseInt: " + suma);
console.log("map(parseInt): " + terminal.map(parseInt).join(" | "));
console.log("map(Number):   " + terminal.map(Number).join(" | "));
console.log(suma <= LIMIT ? "PRZEJAZD DOZWOLONY (" + suma + " kg)" : "STOP: przeciazenie (" + suma + " kg)");
```

## Quiz (no hints)

**1.** A colleague "fixes" the terminal with three variants: (a) `parseInt(w)`, (b) `Number(w)`,
(c) `parseFloat(w)`. Run them against the four terminal entries plus `""` and `null`. Which one
is the only one that *signals* a broken entry instead of quietly repairing it — and why can it
still not be called "always safer"? Name one entry where that same variant is the more dangerous
choice.

> **Key.** On `["1200","12,5","1e3","800kg"]`: (a) `1200, 12, 1, 800`; (b) `1200, NaN, 1000, NaN`;
> (c) `1200, 12, 1000, 80`. On `""`: `NaN` / `0` / `NaN`. On `null`: `NaN` / `0` / `NaN`.
> Only (b) `Number` signals corruption, because `"12,5"` and `"800kg"` produce `NaN`, which
> `Number.isNaN()` catches and which poisons every downstream operation. But "always safer" is
> false: on an empty entry `Number("")` returns `0` — a silent zero mass entering the sum as a
> legitimate reading (same for `null` and `" "`), whereas `parseInt("")` returns `NaN` and blows
> the sum up immediately. **`parseInt` lies on broken data; `Number` lies on empty data.**
> The version without a hole combines both checks:
> `const n = Number(w); if (w.trim() === "" || !Number.isFinite(n)) reject();`
> — `isFinite`, not `isNaN`, because `Number("Infinity")` is `Infinity`.

**2.** `["10","10","10"].map(parseInt)` returns three different results for three identical
strings. Give all three with reasoning, explain the mechanism, then say why `.map(Number)`
returns the same value three times despite receiving exactly the same arguments. How does this
bug differ from every error in sessions S29–S50?

> **Key.** `10, NaN, 2`. `.map()` calls the callback with **three** arguments
> `(element, index, array)`; `parseInt` takes **two** — `(string, radix)`. The index lands as the
> numeric base. `parseInt("10", 0)` → radix 0 means "default", i.e. decimal → `10`;
> `parseInt("10", 1)` → base 1 does not exist (2–36 allowed) → `NaN`; `parseInt("10", 2)` → `"10"`
> in binary → `2`. `.map(Number)` returns `10` three times because `Number` takes one argument and
> ignores the extras. The difference from S29–S50: every previous bug came from a **value** and its
> type (coercion, references, emptiness, names). This one comes from the **number of arguments** —
> syntax is valid, types match, no value is corrupt, and three identical strings still yield three
> different numbers. Rule: never hand `.map()` a pre-existing function that takes more than one
> argument; wrap it in a single-parameter arrow.

**3.** The operator types `12,5` (comma — Polish and Icelandic numeric keypads) where the system
expects `12.5`. Give the result of `parseInt`, `Number`, and `Number(w.replace(",", "."))`. Then:
which of those three results is *hardest* to find two weeks later when someone reports that the
tonnage reports don't add up — and why that one, rather than the one that is numerically furthest
from the truth?

> **Key.** `12`, `NaN`, `12.5`. Hardest to find is `12` from `parseInt`, not `NaN`, even though
> `NaN` is numerically further from the truth. Three reasons, all about **diagnosis** rather than
> arithmetic: (a) `12` is a *plausible* value — it sits in range, passes every type and bounds
> check, and reads like a normal measurement in a report; (b) `NaN` poisons every downstream
> operation and surfaces at the first sum, while `12` quietly shaves half a unit off every
> comma-typed entry; (c) the `parseInt` error is **proportional to traffic**, so it grows with
> volume and never produces a single failure moment — after two weeks you have a thousand
> slightly-low records and zero entries in the error log to start from.

## Card banked (spaced repetition)

**Front:** How does `parseInt(s)` differ from `Number(s)` — and which is safer for form data?

**Back:** Two different operations, not two names for one. `parseInt` is a **prefix parser**: reads
from the left, takes as many characters as it understands, and stops at the first unknown one,
returning what it got with no signal that anything remained (`"80kg"` → `80`, `"12,5"` → `12`,
`"1e3"` → `1`, `"12.9"` → `12`, truncating rather than rounding). `Number()` is a **whole-value
conversion**: either the entire string is a number, or `NaN`. Consequence: `parseInt` does not
silence an error, it *manufactures a plausible wrong number*, so the `Number.isNaN(x)` guard has
nothing to catch (`Number.isNaN(parseInt("80kg"))` → `false`). Answer to "which is safer": neither
unconditionally — on **emptiness the roles reverse** (`parseInt("")` → `NaN` but `Number("")` → `0`;
same for `null` and `" "`). `parseInt` lies on broken data, `Number` lies on empty data. Hole-free
version: `const n = Number(w); if (w.trim() === "" || !Number.isFinite(n)) reject();`. Third trap
comes from **argument count**: `parseInt`'s second parameter is the radix and `.map()` passes the
index as the second argument — `["10","10","10"].map(parseInt)` → `10, NaN, 2`. Always
`parseInt(s, 10)` with an explicit radix, and never `parseInt` for validating API/form data.

## Takeaway

In integration work the expensive failures are not the ones that shout — they are the ones that
look like a correct result. `parseInt` is a factory for those: it returns a number that passes
every range check and every dashboard, and differs from the truth by exactly the tail it swallowed.
That is the kind of bug you find in an audit, not in a log.
