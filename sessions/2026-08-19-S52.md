# S52 — Floating point: the reorder that costs a free-delivery threshold

**Concept:** `0.1 + 0.2 !== 0.3` is not a JavaScript quirk, it is IEEE 754. A decimal fraction whose
denominator is not a power of two has no finite binary representation, so `0.1` is already an
approximation the moment it is typed. And once every number is an approximation, addition stops being
**associative** — changing the *order* of a sum changes the result.

**Format:** what-if.

---

## Story

Online grocery "Spizarnia". Free delivery over 100 zl, otherwise a 15 zl surcharge. On Monday, support
gets three tickets from customers whose receipt says a clean `100.00 zl` **and** shows the delivery
surcharge on the same line. Nobody touched the price list or the threshold. The only change from last
week is one line somebody added so that receipt items print alphabetically instead of in the order they
were added to the cart.

## Round 2 — the same cart, summed in two orders

```js
const PROG_GRATIS = 100;

const koszyk = [
  { nazwa: "Bagietka",       cena: 19.90 },
  { nazwa: "Ser korycinski", cena: 30.30 },
  { nazwa: "Kawa ziarnista", cena: 49.70 },
  { nazwa: "Torba",          cena:  0.10 },
];

function podsumuj(pozycje) {
  let suma = 0;
  for (const p of pozycje) {
    suma += p.cena;
  }
  return suma;
}

const wKolejnosciDodania = podsumuj(koszyk);
const naParagonie = podsumuj([...koszyk].sort((a, b) => a.nazwa.localeCompare(b.nazwa)));

console.log("koszyk:   " + wKolejnosciDodania + " -> " + (wKolejnosciDodania >= PROG_GRATIS ? "DOSTAWA GRATIS" : "doplata 15 zl"));
console.log("paragon:  " + naParagonie + " -> " + (naParagonie >= PROG_GRATIS ? "DOSTAWA GRATIS" : "doplata 15 zl"));
console.log("ta sama kwota? " + (wKolejnosciDodania === naParagonie));
console.log("klient widzi: " + wKolejnosciDodania.toFixed(2) + " zl oraz " + naParagonie.toFixed(2) + " zl");
```

## Quiz

**1.** A colleague proposes three fixes for the threshold: (a) `suma.toFixed(2) === "100.00"`,
(b) `Number(suma.toFixed(2)) >= 100`, (c) `Math.round(suma * 100) >= 10000`. What does each return for
`100` and for `99.99999999999999`? Which one breaks on a different cart?

> All three return `true` for both values, so all three "fix" today's case — which is exactly why the
> question has to be what each one breaks elsewhere. (a) is structurally wrong: it turns a *threshold*
> into an *equality*, so a 150.50 cart gives `"150.50" === "100.00"` -> `false` and a customer spending
> half again over the threshold loses free delivery. (b) and (c) point the right way but shift the
> threshold down by half a grosz: `(99.995).toFixed(2)` -> `"100.00"` and
> `Math.round(99.995 * 100)` -> `10000`, both `true`. The version without the hole works in integer
> cents *from the start* — `Math.round(cena * 100)` on every line item, summed as integers — rather
> than rounding the total at the end. And `toFixed` returns a **string**: `=== 0.3` is `false` because
> `===` does not coerce, `== 0.3` is `true` because it does.

**2.** "It is less than one grosz, so it does not matter." Rebut with two independent counterexamples,
then say whether integer cents remove the problem or just move it.

> Two separate reasons. First, an error of `1e-14` next to a threshold is not an error of *amount*, it
> is an error of *decision*: `99.99999999999999 >= 100` is `false`, `100 >= 100` is `true`, and that
> gap is worth 15 zl while `toFixed(2)` prints the identical string on both sides. Amount and decision
> are different things and only one of them has a tolerance. Second, the errors do not cancel: `0.1`
> added ten times is `0.9999999999999999`, added a thousand times it is `99.9999999999986` — roughly a
> hundred times the single-step error — and with `0.7` the drift goes the *other* way. Direction is
> unpredictable, accumulation is systematic. Integer cents do not remove the problem, they move it to
> one place: the input conversion. `19.90 * 100` -> `1989.9999999999998` while `30.30 * 100` is exact,
> so multiplication fails selectively and still needs `Math.round` per line. After that one step
> everything downstream is integer arithmetic, which is exact up to `Number.MAX_SAFE_INTEGER` — one
> place to check instead of every addition in the system.

**3.** `0.5 + 0.25 === 0.75` is `true`, `0.1 + 0.2 === 0.3` is `false`. State the rule that decides this
without running anything, test it on `0.125 + 0.375 === 0.5`, `1.5 + 2.25 === 3.75`, `0.7 + 0.1 === 0.8`.

> A fraction has an exact binary representation iff its fractional part is a finite sum of
> `1/2, 1/4, 1/8, ...` — that is, iff in lowest terms its denominator is a power of two. It must hold
> for both operands and for the result. Checks: `0.125 + 0.375 === 0.5` -> `true` (`1/8 + 3/8 = 4/8`);
> `1.5 + 2.25 === 3.75` -> `true` (the integer part is irrelevant); `0.7 + 0.1 === 0.8` -> `false`
> (denominator 10 contains a 5; the result is `0.7999999999999999`). Shortcut: no 5 may survive in the
> denominator. This matters more when *reading* someone else's financial code than when writing your
> own, because your own code can be settled with one decision made once ("cents everywhere, round on
> input"). Existing code usually does both at once — some amounts in cents, some parsed with
> `parseFloat`, `toFixed` used once for display and once for comparison. You are not looking for "a
> calculation error", you are looking for **boundaries**: where an amount changes representation, and
> whether a `===` or a threshold sits on that boundary.

## SM-2 card

**Front:** Why is `0.1 + 0.2 !== 0.3`, and which property of addition stops holding because of it?

**Back:** Floats are stored as IEEE 754 binary, and a decimal fraction whose denominator is not a power
of two has no finite binary form, so `0.1` is an approximation the moment it is typed
(`(0.1).toFixed(20)` -> `0.10000000000000000555`, `(0.2)` rounds up, `(0.3)` rounds down). Hence
`0.1 + 0.2` -> `0.30000000000000004`, but `0.5 + 0.25 === 0.75` is `true` because halves and quarters
are exact. The property that dies is **associativity**: `(0.1+0.2)+0.3 === 0.1+(0.2+0.3)` -> `false`,
`0.1+0.2+0.3` -> `0.6000000000000001` vs `0.3+0.2+0.1` -> `0.6`. So any line that merely *reorders*
elements (`.sort()`, `.reverse()`, a different `ORDER BY`) can change a financial result. `toFixed` is
not a fix — it returns a string and rounds halves counterintuitively (`(1.005).toFixed(2)` -> `"1.00"`).
For comparison use a tolerance (`Math.abs(a - b) < 1e-9`); for money use integer cents with
`Math.round(price * 100)` per item, because `19.90 * 100` -> `1989.9999999999998` on its own.

## Takeaway

For five days the question was what the code stays silent about, and yesterday it was what the code
answers instead of what you asked. Today the question is narrower still: what does this code *do* while
looking like it does nothing. The `.sort()` line does not calculate. It does not touch prices, the
threshold, or any branch. It only changes order — which is precisely why it passed review without a
single comment. In integration work, most real incidents have exactly that shape: a change whose commit
message reads like cosmetics. Reading a financial diff, do not only ask what a line computes. Ask
whether anything now meets anything else in a different order than it did yesterday.
