# S53 — Two tickets, one number

**Concept:** integer precision above `Number.MAX_SAFE_INTEGER` — why a 19-digit API id
loses its trailing digits inside `JSON.parse`, and why two different records collapse into one.

**Setting:** a courier company wires up an external ticketing API. Docs say `id` is a unique
19-digit identifier. Support reports that "sometimes one ticket disappears" — no error, no empty
field, three records sent and two shown. Network inspector confirms all three arrive.
`rekordy.length` in the code also says `3`. Only the dedupe step turns it into `2`.

## Encounter 1 — is this number still that number

```js
const MAX = Number.MAX_SAFE_INTEGER;
console.log("MAX_SAFE_INTEGER     =", MAX);
console.log("MAX + 1              =", MAX + 1);
console.log("MAX + 2              =", MAX + 2);
console.log("MAX + 1 === MAX + 2  ?", MAX + 1 === MAX + 2);
console.log("isSafeInteger(MAX+1) ?", Number.isSafeInteger(MAX + 1));

const odpowiedz = '{"id": 1305818919274905601, "temat": "faktura"}';
const rekord = JSON.parse(odpowiedz);
console.log("id z JSON-a          =", rekord.id);
console.log("id === literal       ?", rekord.id === 1305818919274905601);
console.log("String(id)           =", String(rekord.id));
```

## Encounter 2 — the vanishing ticket

```js
const zAPI = [
  '{"id": 1305818919274905601, "kto": "Nowak"}',
  '{"id": 1305818919274905602, "kto": "Kowalska"}',
  '{"id": 1305818919274905903, "kto": "Wisniewski"}'
];
const rekordy = zAPI.map((s) => JSON.parse(s));
console.log("rekordow z API       =", rekordy.length);

const unikalne = new Set(rekordy.map((r) => r.id));
console.log("unikalnych id        =", unikalne.size);
console.log("id-y po parsowaniu   =", [...unikalne].join(" | "));

const mapa = new Map();
for (const r of rekordy) mapa.set(r.id, r.kto);
console.log("wpisow w mapie       =", mapa.size);
console.log("kto ma id ...601     =", mapa.get(1305818919274905601));
```

## Verified

Run with node v22.22.3 before publishing.

```
MAX_SAFE_INTEGER     = 9007199254740991
MAX + 1              = 9007199254740992
MAX + 2              = 9007199254740992
MAX + 1 === MAX + 2  ? true
isSafeInteger(MAX+1) ? false
id z JSON-a          = 1305818919274905600
id === literal       ? true
String(id)           = 1305818919274905600
```

```
rekordow z API       = 3
unikalnych id        = 2
id-y po parsowaniu   = 1305818919274905600 | 1305818919274905900
wpisow w mapie       = 2
kto ma id ...601     = Kowalska
```

Side checks, run separately: `2**53 === 2**53 + 1` is `true`; the literal `9007199254740993`
prints as `9007199254740992`; `MAX + 3` is `9007199254740994` and `MAX + 4` is `9007199254740996`;
`Number.isInteger(MAX + 1)` is `true` (so it detects nothing); the gap between neighbours near
`1.3e18` is `256`. BigInt: `BigInt("1305818919274905601")` is exact, but
`BigInt("1305818919274905601") === BigInt(1305818919274905600)` is `false`, `b + 1` throws
`TypeError: Cannot mix BigInt and other types, use explicit conversions`, and
`JSON.stringify({id: b})` throws `TypeError: Do not know how to serialize a BigInt`.

## Answer

The information is lost inside `JSON.parse`, not in the API and not in the dedupe step. What comes
over the wire is TEXT (`"id": 1305818919274905601`); `JSON.parse` turns it into a `Number` that has
no such value in its precision range, so it stores the nearest representable one:
`1305818919274905600`. Around `1.3e18` the gap between neighbours is 256, so `...601` and `...602`
land on the same value while `...903` lands on `...900` — hence a `Set` of size 2, and a `Map` in
which `Kowalska` silently overwrote `Nowak`. Dedupe behaved correctly: it received two identical
numbers. `rekordy.length` is `3` because there really are three records; one field inside each is
broken. And `rekord.id === 1305818919274905601` is `true` because the literal in the source code
goes through exactly the same rounding — comparing against a literal is blind by construction.

One-line proof to paste right after `JSON.parse`:
`console.log(rekordy.map(r => Number.isSafeInteger(r.id)))` → `[ false, false, false ]`.

## Quiz

1. Three proposed guards: (a) `!Number.isInteger(r.id)`, (b) `!Number.isSafeInteger(r.id)`,
   (c) `String(r.id).length !== 19`. Which one actually catches the problem?
   **Key:** only (b). (a) passes, because the rounded value is still an integer — just a different
   one. (c) passes too, because rounding does not change the digit count, and the "always 19 digits"
   assumption breaks on older snowflakes (18 digits) and on ids sent as strings.
2. Someone writes `const id = BigInt(rekord.id)` after `JSON.parse` and declares it fixed.
   **Key:** one step too late — `rekord.id` is already a rounded `Number`, so BigInt faithfully
   preserves a wrong value. BigInt must be fed a STRING, i.e. the value has to be captured before
   parsing. Two things then break: mixed arithmetic (`Cannot mix BigInt and other types`) and
   serialization (`Do not know how to serialize a BigInt`). Which is why the standard advice is
   "keep ids as strings", not "use BigInt" — nobody does arithmetic on an identifier.
3. Fifth time in this series that two distinct records collapsed into one. What is different here?
   **Key:** the previous four bugs lived in code someone wrote — wrong equality, wrong key, wrong
   data structure — and careful reading finds them. Here the code is faultless; the bug lives in the
   REPRESENTATION, before the first line of logic ran. Spot the risk by name and origin: `id`,
   `snowflake_id`, `message_id`, `tx_id`, `epoch_ns` — anything that is an external identifier or
   timestamp and arrives in JSON without quotes. Rule of thumb: 15 digits safe, 16 borderline,
   17+ guaranteed trouble.

## Spaced repetition card

**Front:** Why can a 19-digit API `id` collapse two distinct records into one after `JSON.parse`,
and what is the correct fix?

**Back:** JS has a single numeric type (IEEE 754 double) with 53 bits of significand, so the last
integer with its own representation is `Number.MAX_SAFE_INTEGER` = `9007199254740991`. Above it the
engine rounds to the nearest representable neighbour, and the gap grows with magnitude (256 near
`1.3e18`). So `JSON.parse('{"id": 1305818919274905601}')` yields `1305818919274905600`, and 256
consecutive ids share one representation. Blind tests: comparison against a literal (`true`) and
`Number.isInteger` (`true`). Detected by `Number.isSafeInteger` (`false`). Fix: keep the identifier
as a STRING from the wire to the database.

## Takeaway

The previous four dedupe bugs could be found by reading the code more carefully. This one cannot.
The code is correct, the data is correct; what is broken is the format in which one met the other.
Reading an integration, the question is not "what does this line do" but "is what enters it still
what the sender sent".
