# S55 — Timezones: the same date, two different moments

**Concept:** `new Date("2026-08-22")` is **midnight UTC**. `new Date("2026-08-22 00:00")` is **midnight LOCAL**. What decides is whether the string contains a *time*. The local form takes its offset from the machine, so the same code produces different results on your laptop and on the client's server.

**Format:** bug-hunt
**Language:** JavaScript (node v22.23.2)

---

## Story

A shop called *Nocna Zmiana* sells at night — that is its entire niche. The daily report is generated at 3am on the client's VPS, set to `Europe/Warsaw`. You write and test the code in Reykjavik. Everything passes. A week later the client calls: *"the number of orders in the report is right, but those are not the orders."*

## Answer key

**Bug 1 — two date formats mixed.** `new Date("2026-08-22")` is midnight UTC; `new Date("2026-08-22 00:00")` is midnight local. The difference comes purely from the presence of a *time* in the string: an ISO date-only form is UTC by specification, the same moment written with a time and no offset is local by specification. One space and four characters move the point on the timeline by two hours.

**Bug 2, the worse one — the code reads its timezone from the environment.** Variant B never states `Europe/Warsaw` anywhere; it inherits it from the machine. The same file, the same commit and the same data produce one report on your laptop, another on the client's VPS, another on Vercel (UTC by default), and another again after an admin changes a system setting. That is a hidden input to the function which does not appear in its signature and which no unit test running on a single machine will catch.

1. **Why it didn't show up in Reykjavik.** `Atlantic/Reykjavik` is UTC+0 all year with no DST, so at offset zero both forms produce *exactly* the same instant (`a.getTime() === b.getTime()` is `true` there and `false` in Warsaw). The line is correct on your machine and wrong on the client's. That is not luck; that is a missing test case.
2. **What the client sees.** Report B for August 22 contains `Z-1`, placed on August 21 at 22:30 UTC, and is missing `Z-4` from August 22 at 23:30 UTC. Since both counts are 3, the ticket reads *"the report shows the wrong orders"* or *"end-of-day sales disappear and come back the next day"* — never *"the report has the wrong number of rows."* That is why the bug survived a week.
3. **How to write a day boundary.** Make the zone explicit, never inherited: either the whole day in UTC (`new Date("2026-08-22T00:00:00Z")` — the trailing `Z` makes the result identical everywhere), or the day in the client's zone with an explicit offset. The offset cannot be hardcoded, because it is `+02:00` in summer and `+01:00` in winter; that is what a timezone library is for (`Intl` with `timeZone`, `date-fns-tz`, `luxon`), or a database that can do `AT TIME ZONE`. The choice between them is a business decision, not a technical one: a "day" ends at midnight on the *client's* clock, so store and compare everything in UTC and keep the reporting zone written down explicitly in config.

**Three signals that a line is machine-dependent:**

- `new Date("...")` with a string that has a time but no `Z` and no `+HH:MM` → give it an explicit zone.
- `new Date(year, month, day)` from numbers — this constructor is *always* local → use `new Date(Date.UTC(...))`.
- Any getter without `UTC` in the name (`getDate`, `getHours`, `getMonth`, `getDay`) reads the machine clock → use the `getUTC*` form or `toLocaleString` with an explicit `timeZone`.

Bonus: `toISOString()` shown to a human always prints UTC, so it will display the wrong hour.

## Quiz

1. **Same server, different season.** What does `new Date("2026-03-29 02:30").toString()` return, given that this hour does not exist in Poland that day? Then compute both differences in hours. What does that mean for code computing "yesterday" as `now - 24*60*60*1000`?
   **Key:** `Sun Mar 29 2026 03:30:00 GMT+0200 (Central European Summer Time)` — a non-existent hour is not an error; the engine silently rolls it forward. Differences: **23 hours** and **25 hours** (both 24 in Reykjavik). So `24*60*60*1000` is not "a day", it is "24 hours" — twice a year those are different things. A day is a calendar concept (`setDate(d.getDate() - 1)` or a timezone library), not an arithmetic one.

2. **The popular shortcut** `new Date().toISOString().slice(0, 10)` as "today's date" for a filename. What does it return on a Warsaw server at 01:30 on the night of the 22nd to the 23rd, and why is that wrong? Give a version that returns the local date in `RRRR-MM-DD` without manual string assembly.
   **Key:** It returns `2026-08-22`, because locally it is already the 23rd but in UTC it is still `2026-08-22T23:30:00.000Z` — so `raport-2026-08-22.json` overwrites yesterday's report and today's is never written. `toISOString()` *always* prints UTC; using it to extract a local date is a category error, not a typo. Correct: `d.toLocaleDateString('sv-SE')` → `2026-08-23`, with `{ timeZone: "Europe/Warsaw" }` if you want independence from the machine. No `getMonth()` problem either, because `Intl` does the formatting — `getMonth()` counts from zero (August returns `7`), so every manual assembly needs a `+1` and every forgotten `+1` yields a date that is a month off and looks perfectly fine.

3. **Why is working from Iceland the worst possible test environment for this class of bug?**
   **Key:** `Atlantic/Reykjavik` has offset zero all year and does not change clocks, so "local" and "UTC" are the same thing there — precisely the two things whose difference is the whole bug. Correct code and broken code produce identical output on that machine (verified). Practical fix: run tests under at least two zones with non-zero offsets of opposite sign — `TZ=Europe/Warsaw` and `TZ=America/New_York` before `node`, one word in the command. On Windows PowerShell: `$env:TZ='Europe/Warsaw'; node file.js` (verified to work).

## Card

**Front:** How does `new Date("2026-08-22")` differ from `new Date("2026-08-22 00:00")`, and why might that difference never show up on your own computer?

**Back:** The difference is whether the string contains a **time**. An ISO date-only form is midnight **UTC** by specification — the same instant on every machine on earth. The same day written with a time but no `Z` and no offset is midnight **local**, so the engine takes the zone from whatever machine the code happens to run on. Verified under `TZ=Europe/Warsaw`: `2026-08-22T00:00:00.000Z` vs `2026-08-21T22:00:00.000Z`, `a - b` → `7200000`, `a.getTime() === b.getTime()` → `false`, `b.getDate()/b.getUTCDate()` → `22 / 21`. Under `TZ=America/New_York` the difference has the **opposite sign** (`a - b` → `-14400000`, and it is `a.getDate()` that falls back to `21`). Under `TZ=Atlantic/Reykjavik` (UTC+0 all year) there is **no difference at all** (`a.getTime() === b.getTime()` → `true`). That is why the bug is invisible to someone testing in Iceland and explodes on the client's server: a day filter built on the local form catches different records than one built on UTC — and the **count can still match** (verified: both reports contain 3 rows, `Z-1, Z-2, Z-3` vs `Z-2, Z-3, Z-4`), so the ticket says "wrong orders", not "wrong number". Same family: `new Date(y, m, d)` is always local (the UTC equivalent is `Date.UTC(...)`), getters without `UTC` read the machine clock, `toISOString()` always prints UTC (so `.slice(0,10)` at 01:30 returns *yesterday's* date), and a day is not always 24 hours (verified in Warsaw: 29 March has 23, 25 October has 25). Fix: make the zone explicit every time — `"...T00:00:00Z"`, `Date.UTC(...)`, or `toLocaleDateString('sv-SE', { timeZone })`; store and compare in UTC, format in the client's zone from config, and test under two zones, never only your own.

## Takeaway

For three days the lesson was about data that lies — the fraction, the ID, the date as an object. Today the **environment** lies. Same file, same commit, same data, two different reports, depending on what clock the machine has. An integrator who cannot see that ships code that works only where it was written.
