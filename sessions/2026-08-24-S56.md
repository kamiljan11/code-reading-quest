# S56 — Voltera: four charging sessions, one function, four different fates

**Concept:** a timestamp has a UNIT (seconds vs milliseconds) and a TYPE (number, ISO string, `Date`) — and the comparison operator checks neither, and warns about neither.

**Format:** what-if

## Story

"Voltera" runs nine EV chargers around Reykjavik. The chargers report session start over OCPP — a protocol grown out of the C world, so time arrives as epoch in **seconds**. The backend stores the end time in Postgres and returns it as an **ISO string**. The billing code is JS, where `Date.now()` is **milliseconds**. Nobody lied anywhere. The invoices come out wrong anyway — and only some of them look wrong.

## Quiz

1. A JWT `exp` claim is in **seconds** per RFC 7519. Someone writes `if (token.exp > Date.now()) allow() else deny()`. What does this guard do for *every* token, valid or expired? Justify with the magnitudes. Then say what happens if the condition is flipped to `Date.now() > token.exp`, and why the flipped version is more dangerous in production despite being the same bug.
   **Key:** `exp > Date.now()` compares 1787360400 with 1787000000000, so it is `false` always — nobody logs in, the outage is loud and immediate, fixed in fifteen minutes. Flipped, it is `true` always, which in the common `if (Date.now() > exp) deny()` shape rejects everything, and in the opposite shape lets everything through. The "lets everything through" variant is the expensive one: the system works, nobody files a ticket, and the expiry check is dead code. **An outage that blocks everyone is cheap; an outage that admits everyone is expensive.**

2. You have a raw value `x` known only to be "some timestamp". Give a practical test that distinguishes seconds from milliseconds and state until which year it is trustworthy. Then explain why it must not live inside the function that computes charging time — where it belongs instead, and what that function should do with a value it does not recognise.
   **Key:** digit count — 10 digits = seconds, 13 = milliseconds, 16 = microseconds (verified); or `x < 1e12 ? x * 1000 : x`. Trustworthy until year 2286 (1e13 ms), i.e. longer than any system you write today will live — but it is a **heuristic based on what year it is**, not a contract declared by the sender. So it belongs in the input-validation layer (the adapter/parser right behind the fetch or webhook), not in business logic; the business function should receive one normalised representation. An unrecognised value must cause an explicit `throw` (or a `{ ok: false, reason }` result) — never `NaN`, never `0`, and never `Date.now()` as a "sensible default", because each of those silent answers reproduces the L-3 symptom.

3. A team decides to "simplify" and store every timestamp as an ISO string, because "ISO sorts lexicographically, so `<` and `>` will just work". Under exactly what conditions is that sentence true? Give a counterexample: a pair of ISO strings where text comparison disagrees with instant comparison. Then explain why the idea passes every test at a company whose database sits in one time zone, and breaks on the first foreign client.
   **Key:** ISO sorts chronologically **only** when every string has identical length, identical precision and identical offset (ideally all `Z`) — then lexicographic order matches chronological order, because fields run most-significant-first and are left-zero-padded (verified: `"2026-08-22T09:00:00Z" < "2026-08-22T10:00:00Z"` -> true). Counterexample: `"2026-08-22T01:00:00+02:00"` vs `"2026-08-22T00:30:00Z"` — as text `<` gives **false**, as instants the first is **earlier**, so the right answer is **true** (both verified; `01:00+02:00` is `23:00Z` the previous day). Second counterexample from the same family: `"2026-08-22T01:00:00Z"` vs `"2026-08-22T01:00:00.000Z"` — same instant, `===` gives false. It passes testing because as long as all traffic comes from one database in one zone, every string has the same shape and the same suffix, so "text = chronology" is locally true. The first client sending `+02:00` (or the first library that starts appending milliseconds) breaks it without a single error in the logs — the comparisons still return true/false, just not the right ones.

## SM-2 card

**Front:** Two values are supposed to be the same instant, but they came from two different systems. What must you ask before comparing them — and what will the operator do if you don't?

**Back:** Ask about the UNIT (seconds or milliseconds) and the TYPE (number, ISO string, or `Date`). The operator checks neither and reports no error. Unit: epoch in SECONDS (OCPP/chargers, JWT `exp` per RFC 7519, Stripe, anything from the C world) vs epoch in MILLISECONDS (`Date.now()`, JS, Java) — verified: `1787360400 === new Date("2026-08-22T01:00:00Z").getTime()` -> false, but `* 1000` -> true, and `1787360400 < zKodu` -> true, so a seconds epoch *impersonates* a valid, earlier date (on its own: `new Date(1787360400).toISOString()` -> `1970-01-21T16:29:20.400Z`). Type: `"2026-08-22T01:00:00Z" === zKodu.toISOString()` -> false, because `toISOString()` always appends `.000`; `zBazy > zKodu` -> false **and** `zBazy < zKodu` -> false at once, because both sides go through `Number()` and `Number("2026-08-22T01:00:00Z")` is `NaN`; the constructor reads a number and a string by two different algorithms. The most dangerous case is not the one that looks worst: when both sides are in seconds, `5400 / 60000` is `0.09`, `Math.round` makes it `0`, the guard `minuty >= 0` lets it through, and the customer is invoiced zero for 90 minutes of charging — the only one of the four rows that never reaches an error report. The fix is not at the comparison site but at the **input**: one `toMs(x)` function accepting ISO string / seconds / milliseconds / `Date`, with an explicit `throw` on everything else.

## Takeaway

Every integration you build as an AI Automation Engineer joins at least two systems — which means at least two time conventions. Asking "what unit and what type did this value arrive in" *before* you look at the operator costs thirty seconds and saves a week of hunting invoices that billed zero.
