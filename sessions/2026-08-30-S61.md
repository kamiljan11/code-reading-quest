# S61 - 🧗 scianka wspinaczkowa "Klettur": Podium, ktore oglosilo zwyciezca z najgorszym wynikiem

**Concept:** Operatory i porownania — .sort() bez komparatora porownuje TEKST, nie liczby, i mutuje w miejscu

> .sort() bez komparatora zamienia KAZDY element na tekst przez String(x) i porownuje napisy znak po znaku, wiec decyduje pierwsza cyfra, nie wielkosc liczby. Do tego sortuje W MIEJSCU i zwraca TE SAMA tablice, nie kopie. Blad jest niewidoczny, gdy wszystkie liczby maja te sama liczbe cyfr — dlatego przechodzi przez testy.

**Format:** `predict-output` | **Phase:** 1 | **Date:** 2026-08-30

## Scenario

A climbing gym runs a competition. Holds have chips, the backend builds a ranking, and the referee reads the podium off the screen. The code is five lines long, it has been in production for two seasons, and it passed review because on the test data it produced a correct order. Today the winner scored 1000 points and is not on the podium at all. The person announced as first place scored 9.

## Map

```text
   CO ROBI .sort() BEZ KOMPARATORA
   ==============================================================================

   [100, 9, 80, 1000, 20]
        |
        |  krok 1: KAZDY element -> String(x)     (undefined jest pomijane!)
        v
   ["100", "9", "80", "1000", "20"]
        |
        |  krok 2: porownanie napisow ZNAK PO ZNAKU (punkty kodowe UTF-16)
        |          "1" < "2" < "8" < "9"  ->  decyduje PIERWSZY znak, nie dlugosc
        v
   ["100", "1000", "20", "80", "9"]   ->   [100, 1000, 20, 80, 9]


   KIEDY BLAD JEST NIEWIDOCZNY (i dlatego przezywa code review)
   ------------------------------------------------------------------
   [3, 1, 2]           -> [1, 2, 3]        OK  (same jednocyfrowe)
   [30, 10, 20]        -> [10, 20, 30]     OK  (ta sama dlugosc)
   [-5, -100, 3, 40]   -> [-100, -5, 3, 40] OK (przypadkiem! wspolny minus i
                                               cyfry ukladaja sie tu zgodnie)
   [100, 9]            -> [100, 9]         ZLE (rozna liczba cyfr = pierwszy blad)

   KOMPARATOR: CO ZWRACAC
   ------------------------------------------------------------------
   ujemna   -> a przed b        (a, b) => a - b     rosnaco
   zero     -> zostaw kolejnosc (a, b) => b - a     malejaco
   dodatnia -> b przed a

   PULAPKI KOMPARATORA
   ------------------------------------------------------------------
   (a, b) => a > b     -> boolean -> 0 albo 1, NIGDY ujemna -> nic sie nie dzieje
   (a, b) => a.x - b.x -> gdy jedno x jest undefined -> NaN -> traktowane jak 0
                          -> czesc tablicy sie posortuje, czesc NIE, zero bledu
   undefined w tablicy -> ZAWSZE laduje na koncu, komparator go nie widzi

   MUTACJA
   ------------------------------------------------------------------
   arr.sort()      -> zmienia arr W MIEJSCU i zwraca TE SAMA tablice (=== arr)
   arr.toSorted()  -> zwraca NOWA tablice, arr nietkniete   (ES2023 / Node 20+)
```

## Answer key

(b) DWA kroki. Krok 1: .sort() bez komparatora sortuje po tekscie, wiec [100,9,80,1000,20] -> [100,1000,20,80,9]; najwiekszy wynik 1000 laduje na DRUGIEJ pozycji od poczatku, bo "1000" zaczyna sie od "1" tak samo jak "100". Krok 2: .reverse() odwraca cala te bledna kolejnosc na [9,80,20,1000,100], a .slice(0,3) ucina dokladnie tam, gdzie 1000 juz nie siega. 9 (ostatnie miejsce) trafia na szczyt podium, bo napis "9" byl "najwiekszy" i stal na koncu, a reverse przeniosl koniec na poczatek. Poprawka to jedna linia: .sort((a,b) => b - a) zamiast .sort().reverse() — linia 10 daje [1000, 100, 80]. (c) Linia 3 klamie ciszej i dlatego jest grozniejsza: zwraca ['Halla','Jon','Oskar','Birta'], czyli liste CZESCIOWO posortowana — za kazdym razem, gdy do porownania wchodzil rekord bez pola pkt, komparator zwracal NaN, a silnik traktuje NaN jak 0 ("zostaw te dwa w spokoju"). Wynik wyglada jak ranking, ma poprawna dlugosc 4, nie rzuca i nie loguje niczego. Linia 11 z (b.pkt ?? -Infinity) daje poprawny ranking z brakiem danych zepchnietym na koniec SWIADOMIE. Wyjatek bylby tanszy: awaria, ktora krzyczy, kosztuje raz i wskazuje linie; ranking posortowany w 60% kosztuje przy kazdym odczycie i nikt nie wie, ze go czyta.

## Quiz

1. [-5, -100, 3, 40].sort() zwraca [-100, -5, 3, 40], czyli POPRAWNA kolejnosc rosnaca — mimo ze sortowanie odbylo sie po tekscie. Dlaczego akurat tutaj tekst i liczba daja ten sam wynik, i jaka jedna liczba dopisana do tej tablicy natychmiast to psuje?

   <details><summary>key</summary>

   Przy liczbach ujemnych kolejnosc tekstowa zgadza sie z liczbowa przypadkiem: wszystkie zaczynaja sie od tego samego znaku '-', wiec decyduje dopiero druga pozycja — "-100" kontra "-5" to "1" < "5", czyli -100 przed -5, co akurat jest poprawne. Reszta (3, 40) tez trafia dobrze, bo "3" < "4". Psuje to kazda liczba lamiaca zgodnosc "pierwsza cyfra = wielkosc": np. 5 (bo "40" < "5" jako tekst, a 5 < 40 jako liczba) albo -9 (wyladuje po "-100" i po "-5", chociaz -9 jest mniejsze od -5). Wniosek: "sprawdzilem na przykladzie i wyszlo dobrze" nie jest dowodem — to dowod, ze probka byla za latwa.

   </details>

2. Funkcja najlepszy(lista) ma nazwe obiecujaca tylko ODCZYT, a po jej wywolaniu kolejnoscZgloszen ma inna kolejnosc niz przed. Ktora linia w jej ciele to robi i jak zapisac te sama funkcje tak, zeby nie dotykala argumentu — podaj DWA sposoby.

   <details><summary>key</summary>

   Robi to lista.sort(...) — sort dziala W MIEJSCU na tablicy, ktora dostal, i zwraca TE SAMA referencje (zweryfikowane: posortowane === czasy -> true), wiec funkcja "tylko czytajaca" przestawia dane dzwoniacego: kolejnoscZgloszen wychodzi jako [21,7,3,5,12], a wchodzilo jako [7,12,3,21,5]. Dwa sposoby: (1) [...lista].sort((a,b) => b.pkt - a.pkt)[0].imie — kopia przed sortowaniem; (2) lista.toSorted((a,b) => b.pkt - a.pkt)[0].imie — ES2023, zwraca nowa tablice (zweryfikowane: kopia zostaje [5,1,3]). Trzeci, najlepszy przy jednym elemencie: w ogole nie sortowac, tylko lista.reduce((n,w) => w.pkt > n.pkt ? w : n).imie. Ta sama rodzina co splice, push, reverse i fill — metody mutujace wygladaja w linii wywolania identycznie jak map/filter/slice, ktore nie mutuja.

   </details>

3. Komparator (a, b) => b.pkt - a.pkt przy jednym rekordzie bez pola pkt zwraca NaN. Co silnik robi z NaN zwroconym z komparatora i dlaczego to jest ten sam ksztalt porazki, ktory widziales przy parseInt("80kg") w S51 — chociaz tam nie bylo zadnego sortowania?

   <details><summary>key</summary>

   Komparator zwracajacy NaN nie jest bledem: silnik konwertuje wynik na liczbe i sprawdza ZNAK, a NaN nie jest ani ujemny, ani dodatni, wiec zachowuje sie jak 0 — "nie zamieniaj tych dwoch miejscami" (zweryfikowane: [2,1].sort((a,b) => NaN) -> [2,1], identycznie jak sort(() => 0)). Ten sam ksztalt co parseInt("80kg") -> 80: funkcja nie mowi "nie dam rady", tylko oddaje WIARYGODNIE WYGLADAJACY wynik, ktory leci dalej bez sygnalu. Roznica wobec S51 jest jedna: tam zla liczba byla widoczna w wyniku (2013 zamiast 3012.5), tu bledna jest tylko KOLEJNOSC, a wszystkie wartosci sa poprawne — czyli nie ma czego z niczym porownac.

   </details>

## Spaced-repetition card

**Front:** Co dokladnie robi .sort() bez komparatora i kiedy ten blad jest niewidoczny?

**Back:** Zamienia KAZDY element na tekst przez String(x) i porownuje napisy znak po znaku (punkty kodowe UTF-16), wiec decyduje PIERWSZA cyfra, nie wielkosc liczby: [100, 9, 80, 1000, 20].sort() -> [ 100, 1000, 20, 80, 9 ], a [10, 9, 1].sort() -> 1 < 10 < 9. Blad jest niewidoczny, gdy wszystkie liczby maja TE SAMA liczbe cyfr ([30,10,20] -> [10,20,30]), gdy sa jednocyfrowe ([3,1,2] -> [1,2,3]), a przy ujemnych potrafi wyjsc poprawnie przez przypadek ([-5,-100,3,40] -> [-100,-5,3,40]) — dlatego przechodzi przez testy i wychodzi na produkcji. Poprawnie: sort((a,b) => a - b) rosnaco, sort((a,b) => b - a) malejaco; NIGDY sort().reverse(). Komparator ma zwracac LICZBE ze znakiem: (a,b) => a > b daje boolean rzutowany na 0/1, nigdy ujemna, wiec nie robi NIC, a (a,b) => a.x - b.x przy brakujacym polu zwraca NaN, ktore silnik traktuje jak 0 — tablica sortuje sie CZESCIOWO, bez bledu i bez logu. undefined zawsze laduje na koncu i komparator go nie widzi. Osobno: sort mutuje W MIEJSCU i zwraca TE SAMA tablice (arr.sort() === arr -> true), wiec funkcja "tylko czytajaca" przestawia dane dzwoniacego — ratunek to [...arr].sort() albo toSorted(). Na napisach z liczbami (plik10, plik9) poprawna kolejnosc daje dopiero localeCompare(b, undefined, { numeric: true }).

## Why it matters

Every integrator touches sort() in the first week at a client: a leaderboard, a "top 5 customers" panel, invoices ordered by amount, pagination by id. None of those will throw when you get it wrong. They will all keep rendering plausible numbers in a plausible order until somebody adds them up by hand. This session is the fifth in a row about the same shape of failure - the loud bug costs you once, the quiet one costs you every time somebody reads the screen - and it is the first where every single value on screen is correct and only the ORDER is a lie, so there is nothing to compare against anything.
