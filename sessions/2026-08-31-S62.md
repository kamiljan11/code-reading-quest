# S62 - Tablice — metody mutujace kontra niemutujace i glebokosc kopii

**Date:** 2026-08-31  |  **Phase:** 1  |  **Format:** order-of-execution  |  **Theme:** 🎿 Wypozyczalnia sprzetu Skidaleiga

## Concept

Metody tablicowe dziela sie na dwie rodziny, ktore w linii wywolania wygladaja IDENTYCZNIE: MUTUJACE (sort, reverse, splice, push, pop, shift, fill) zmieniaja tablice W MIEJSCU, NIEMUTUJACE (map, filter, slice, concat, toSorted, toReversed) zwracaja NOWA. A kopia plytka ([...arr], slice()) chroni TABLICE, ale NIE rekordy w srodku.

## Setup

Ski rental "Skidaleiga" near Blafjoll. Every rental is one record: number, customer, days, deposit. In the morning the boss asks for a report of the two longest rentals. In the evening the storeman says the rental list is in a different order than it was, and every deposit reads zero.

## Starcie 2 — raport dobowy wypozyczalni Skidaleiga

  { nr: "W-1", klient: "Halla", dni: 3,  kaucja: 12000 },

  return lista.sort((x, y) => y.dni - x.dni).slice(0, 2);        // <-- A

  lista.forEach(w => { w.kaucja = 0; });                          // <-- B

  lista.shift();                                                  // <-- C
  return lista;

const g = [1, 2, 3];

## Diagram

```text
   DWIE RODZINY METOD TABLICOWYCH (w linii wywolania NIE DA SIE ICH ODROZNIC)
   ==============================================================================

   MUTUJACE (zmieniaja oryginal)      NIEMUTUJACE (zwracaja nowa tablice)
   -------------------------------    -----------------------------------
   sort()      -> TA SAMA tablica     map()        -> nowa
   reverse()   -> TA SAMA tablica     filter()     -> nowa
   fill()      -> TA SAMA tablica     slice()      -> nowa
   copyWithin()-> TA SAMA tablica     concat()     -> nowa
   splice()    -> WYCIETE elementy    toSorted()   -> nowa   (ES2023)
   push()      -> NOWA DLUGOSC        toReversed() -> nowa   (ES2023)
   pop()/shift()-> USUNIETY element   toSpliced()  -> nowa   (ES2023)
   unshift()   -> NOWA DLUGOSC        with()       -> nowa   (ES2023)
                                      join()/indexOf()/includes() -> nie tablica
   forEach()   -> undefined  (nie mutuje SAMA, ale cialo moze mutowac rekordy)

   PARY, KTORE ROZNIA SIE JEDNA LITERA ALBO JEDNYM SLOWEM
   ------------------------------------------------------------------
   slice(1,3)      KOPIUJE wycinek, oryginal zostaje dlugosci 4
   splice(1,2)     WYCINA z oryginalu, zostaje ['narty','gogle']
   sort()          mutuje         toSorted()    nie mutuje
   reverse()       mutuje         toReversed()  nie mutuje


   JAK GLEBOKO SIEGA "KOPIA"
   ==============================================================================

   [...arr]  /  arr.slice()  /  Array.from(arr)      <- KOPIA PLYTKA
        |
        +--> NOWA tablica            kopia !== arr           OK
        +--> TE SAME rekordy         kopia[0] === arr[0]     PULAPKA

   structuredClone(arr)                              <- KOPIA GLEBOKA
        +--> NOWA tablica i NOWE rekordy   klon[0] !== arr[0]

   PRZECIEK PRZEZ WSPOLNA REFERENCJE (dziala tak samo na obiektach)
   ------------------------------------------------------------------
   const migawka = { ...stan };
   migawka.otwarte.push("W-9")   -> MUTACJA wspolnej tablicy  -> PRZECIEKA
   migawka.zamkniete = ["W-2"]   -> PRZYPISANIE nowego pola   -> nie przecieka

   REGULA CZYTANIA: nazwa funkcji obiecuje. Cialo dotrzymuje albo nie.
```

## Answer key

KOLEJNOSC: A psuje kolejnosc, B psuje kaucje, C nie psuje nic. Linia A (lista.sort((x,y) => y.dni - x.dni)) wykonuje sie pierwsza i zamienia oryginalne [ 'W-1','W-2','W-3','W-4' ] na [ 'W-3','W-1','W-4','W-2' ] (linia 2) — sort mutuje w miejscu i zwraca TE SAMA tablice, a .slice(0,2) doklejony za nim tworzy nowa tablice dopiero PO mutacji, wiec nie ratuje niczego; funkcja nazywa sie najdluzsze i obiecuje sam odczyt. Linia B (w.kaucja = 0 w forEach) wykonuje sie druga i zeruje kaucje we wszystkich czterech ORYGINALNYCH rekordach ([ 0, 0, 0, 0 ], linia 3), mimo ze dostala kopie tablicy. Linia C (lista.shift()) jest jedyna bez szkody — nie dlatego, ze shift jest lagodniejszy od sort, tylko dlatego, ze wywolano ja na wydania.slice(), a shift zmienia DLUGOSC tablicy, czyli dokladnie te jedna rzecz, ktora kopia plytka chroni: kopia traci element (3), wydania zostaje przy 4 (linia 4). Nie ma metod "niebezpiecznych" i "bezpiecznych" — jest pytanie, czy to, co metoda zmienia, lezy po stronie kopii, czy po stronie wspolnych rekordow. (c) Kopia obronila przed zmiana DLUGOSCI i KOLEJNOSCI, nie przed zmiana ZAWARTOSCI rekordow: [...arr][0] === arr[0] -> true (tak samo slice() i Array.from()). Minimalna zmiana: zwrocKaucje(structuredClone(wydania)) (linia 12: structuredClone(wydania)[0] === wydania[0] -> false) albo zwrocKaucje(wydania.map(w => ({ ...w }))). Doprecyzowanie: map(w => ({...w})) tez jest plytka — wystarczy tu, bo rekordy sa plaskie, ale przy zagniezdzonym polu przeciek wroci jeden poziom nizej.

## Quiz

1. **slice i splice roznia sie jedna litera, a robia dwie przeciwne rzeczy. Podaj z pamieci, co kazda ZWRACA i co zostawia po sobie w oryginale — i ktora mozna bezpiecznie wywolac w funkcji o nazwie podglad(lista).**

   slice(od, do) ZWRACA nowa tablice z wycinkiem i zostawia oryginal w calosci (sprzet.length -> 4 po slice(1,3)); splice(od, ile) ZWRACA tablice USUNIETYCH elementow i zostawia oryginal skrocony ([ 'narty', 'gogle' ]). Obie zwracaja [ 'kijki', 'kask' ], wiec po samym wyniku ich nie odroznisz — roznica jest wylacznie w tym, co zostaje po drugiej stronie. W podglad(lista) bezpieczny jest WYLACZNIE slice.

2. **push, pop, sort i map wywoluje sie identycznie: arr.cos(...). Co zwraca kazda z tych czterech i ktore mozna bezpiecznie wpiac w lancuch arr.cos(...).filter(...)?**

   push -> NOWA DLUGOSC (liczba, 3); pop i shift -> USUNIETY element (3 i 1, zostaje [ 2 ]); sort -> TA SAMA tablica (posort === ceny -> true); map -> NOWA tablica (q zostaje [ 1, 2, 3 ]). W lancuch .filter(...) bezpiecznie wpina sie tylko map. arr.push(x).filter(...) RZUCA TypeError, bo filter nie istnieje na liczbie. arr.sort(...).filter(...) ZADZIALA i wlasnie dlatego jest grozny: lancuch przechodzi, wynik jest poprawny, a oryginal cichaczem zmienil kolejnosc — ten sam ksztalt co S61. forEach zwraca undefined, wiec arr.forEach(...).filter(...) tez rzuca.

3. **Kopia plytka chroni tablice, ale nie rekordy. Kiedy [...arr] JEST wystarczajaca ochrona (warunek jednym zdaniem) i jak brzmi ten sam ksztalt reguly z S60 (JSON.parse(JSON.stringify(x))) i S35 (porownywanie obiektow)?**

   [...arr] wystarczy dokladnie wtedy, gdy ELEMENTY tablicy sa PRYMITYWAMI (liczby, napisy, boolean) — prymitywu nie da sie zmutowac, mozna go tylko zastapic, a zastapienie dotyczy juz tylko kopii. Dlatego linia 6 jest niegrozna: wydania.map(w => w.nr) produkuje tablice STRINGOW, wiec etykiety.sort() przestawia napisy i nie dotyka rekordow. Ten sam ksztalt co S60 (JSON.parse(JSON.stringify(x)) dziala dopoki dane sa plaskie i z typow, ktore JSON zna) i S35 (=== na obiektach porownuje referencje, nie zawartosc): JS domyslnie operuje na WSKAZANIACH, a wszystko, co nazywamy kopia, jest kopia jednego poziomu, dopoki jawnie nie powiemy inaczej.

## Spaced repetition card

**Front:** Ktore metody tablicowe mutuja oryginal, a ktore nie — i jak gleboko siega [...arr]?

**Back:** MUTUJA W MIEJSCU: sort, reverse, fill, copyWithin (zwracaja TE SAMA tablice, arr.sort() === arr -> true), splice (zwraca WYCIETE elementy), push/unshift (zwracaja NOWA DLUGOSC), pop/shift (zwracaja USUNIETY element). NIE MUTUJA: map, filter, slice, concat, toSorted, toReversed, toSpliced, with (ES2023, Node 20+) oraz odczyty join, indexOf, includes. forEach zwraca undefined i sama nie mutuje, ale cialo petli moze mutowac rekordy. Pary: slice(1,3) KOPIUJE i zostawia oryginal dlugosci 4, splice(1,2) WYCINA i zostawia [ 'narty','gogle' ] — obie zwracaja to samo. Skutek: funkcja o nazwie obiecujacej odczyt (najdluzsze, podglad, raport) wywolujaca lista.sort(...) trwale przestawia dane dzwoniacego. GLEBOKOSC: [...arr], arr.slice() i Array.from(arr) daja NOWA tablice, ale TE SAME rekordy (kopia[0] === arr[0] -> true) — chronia przed zmiana dlugosci i kolejnosci, NIE przed rekord.pole = x; wystarczaja tylko gdy elementy sa prymitywami. Glebiej: structuredClone(arr) (klon[0] === arr[0] -> false) albo arr.map(o => ({...o})) przy plaskich rekordach. Na obiektach tak samo: { ...stan } przepuszcza migawka.otwarte.push(...) do stan.otwarte, ale migawka.zamkniete = [...] juz nie.

## Takeaway

Wczoraj klamala kolejnosc na ekranie. Dzis klamie nazwa funkcji. najdluzsze() brzmi jak odczyt, zwrocKaucje([...wydania]) brzmi jak ostroznosc, a razem robia to, czego nikt nie zamawial: przestawiaja magazyn i zeruja kaucje. W robocie automatyzatora to jest codziennosc — dostajesz cudzy kod z n8n Function Node albo z pipeline'u i musisz odpowiedziec na jedno pytanie: czy ta funkcja tylko patrzy, czy juz dotyka. Nazwa nie odpowie. Odpowie tylko lista metod, ktore znasz na pamiec.
