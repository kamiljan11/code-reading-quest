# S66 — Log, ktory melduje koniec, zanim cokolwiek sie zaczelo

**Data:** 2026-09-04  
**Faza:** 1 — Alfabet czytania  
**Koncept:** Kolejnosc wykonania - trzy kolejki Node (synchroniczna, mikrozadania, makrozadania)  
**Format:** `order-of-execution`  
**Motyw:** 📦 Hurtownia "Nordur" w Reykjaviku - nocny eksport zamowien do kuriera

## Koncept

O tym, KIEDY linia sie wykona, nie decyduje miejsce, w ktorym zostala NAPISANA, tylko KOLEJKA, do ktorej trafila - a kolejki sa TRZY i kazda nastepna rusza dopiero wtedy, gdy poprzednia jest PUSTA: (1) kod SYNCHRONICZNY leci od gory do dolu bez przerwy az do konca pliku; (2) MIKROZADANIA (`process.nextTick`, potem `Promise.then`/`catch`/`finally`, `queueMicrotask` i wszystko po `await`) oprozniaja sie w CALOSCI dopiero po nim; (3) MAKROZADANIA (`setTimeout`, `setInterval`, I/O) wchodza na samym koncu. Dlatego `setTimeout(fn, 0)` przegrywa z KAZDYM promisem, nawet zarejestrowanym nizej, a `await` nie jest pauza, tylko `return` z reszta ciala funkcji zapisana jako mikrozadanie.

## Fabula

Hurtownia "Nordur" w Reykjaviku wysyla zamowienia do kuriera nocnym skryptem z crona. Skrypt dziala od pol roku i nikt go nie ruszal. W poniedzialek rano ksiegowa dzwoni: kurier twierdzi, ze nie dostal wczorajszych zamowien, ale w logu pisze, ze eksport sie skonczyl. Otwierasz log. Ma osiem linii, konczy sie spokojnie i nie ma w nim ani jednego slowa `error`. Kazde zdanie w tym logu jest prawdziwe. Mimo to log wysyla diagnostyke w zla strone, bo linie w nim NIE stoja w kolejnosci, w ktorej stoja w pliku.

```js
  .then(() => { console.log("7) then B1"); return "x"; })
  .then((v) => console.log("8) then B2", v));

(async () => {
  console.log("9) w async PRZED await");
  await null;
  console.log("10) w async PO await");
})();

console.log("11) koniec pliku");
```

## Starcie 2 - hurtownia "Nordur": nocny eksport zamowien do kuriera

```js
// STARCIE 2 - hurtownia "Nordur": nocny eksport zamowien do kuriera (plik .js, node)
const wyslane = [];

function wyslijDoKuriera(id) {          // udaje zapytanie HTTP - konczy sie dopiero po 5 ms
  return new Promise((ok) => setTimeout(() => { wyslane.push(id); ok(id); }, 5));
}

function zamknijPolaczenie() { console.log("[G] zamykam polaczenie z kurierem"); }

async function eksport() {
  console.log("[A] start eksportu");

  const p1 = wyslijDoKuriera("Z-1");
  const p2 = wyslijDoKuriera("Z-2");
  console.log("[B] oba zapytania wystartowaly, wyslane =", wyslane.length);

  p1.then((id) => console.log("[C] potwierdzenie", id));

  await null;
  console.log("[D] po await null, wyslane =", wyslane.length);

  const id2 = await p2;
  console.log("[E] po await p2:", id2, "| wyslane =", wyslane.length);

  return "raport";
}

eksport().then((r) => console.log("[F]", r, "| wyslane =", wyslane.length));
zamknijPolaczenie();
console.log("[H] skrypt doszedl do konca pliku, wyslane =", wyslane.length);
```

## Klucz

Starcie 1 wychodzi w kolejnosci `1, 9, 11, 6, 4, 5, 7, 10, 8, 2, 3`. Trzy rzeczy do zauwazenia: `9)` drukuje sie jako druga, bo cialo `async` leci SYNCHRONICZNIE az do `await`; `6) nextTick` wyprzedza wszystkie promisy, chociaz w pliku stoi POD nimi (osobna, wyzsza kolejka Node); a `10) w async PO await` laduje miedzy `7) then B1` a `8) then B2`, bo `await null` zajal jedno miejsce w kolejce mikrozadan dokladnie tak jak zwykly `.then`. Starcie 2 wychodzi w kolejnosci `A, B, G, H, D, C, E, F`, przy czym `wyslane.length` wynosi `0` przy `[B]`, `[H]` i `[D]`, a `2` przy `[E]` i `[F]`. (b) NIE, log nie klamie o faktach - klamie o czasie: kazda linia byla prawdziwa w chwili drukowania, `[H] wyslane = 0` stwierdza wylacznie, ze SKRYPT DOSZEDL DO OSTATNIEJ LINII PLIKU, a nie ze praca zostala wykonana. Linia logu "gotowe" postawiona w kodzie synchronicznym pod wywolaniem asynchronicznym nie jest raportem z pracy, tylko raportem z przeczytania kodu; jedyne wiarygodne linie to `[E]` i `[F]`, bo stoja PO `await` na tej konkretnej pracy. (c) `process.exit(0)` ucina program po `[H]`: etykiety `[C]`, `[D]`, `[E]` i `[F]` NIE DRUKUJA SIE WCALE, `wyslane` zostaje `0` (zero wyslanych zamowien), a proces konczy sie kodem `0` - wiec cron i monitoring raportuja sukces. Naprawa bez usuwania `process.exit`: `eksport().then(() => { zamknijPolaczenie(); process.exit(0); })`.

## Quiz

1. `setTimeout(fn, 0)` i `Promise.resolve().then(fn)` stoja obok siebie, przy czym `setTimeout` jest zapisany WYZEJ. Ktory `fn` wykona sie pierwszy i dlaczego - a osobno: czy `0` w `setTimeout(fn, 0)` faktycznie znaczy zero milisekund?
   - **Klucz:** Pierwszy wykona sie `then`, mimo ze `setTimeout` stoi wyzej - bo `then` jest MIKROZADANIEM, a mikrozadania oprozniaja sie w calosci ZANIM event loop dojdzie do fazy timerow. Kolejnosc w pliku nie ma tu znaczenia; znaczenie ma tylko kolejka. `0` nie znaczy zera: najmniejsze opoznienie jest zaciskane do co najmniej 1 ms (zweryfikowane empirycznie), a realnie timer moze spoznic sie dowolnie, jesli event loop jest zajety - `setTimeout(fn, 0)` znaczy "nie wczesniej niz za chwile i nie wczesniej niz wszystko, co juz czeka".
2. W Node sa trzy sposoby na "zrob to za chwile": `process.nextTick(fn)`, `queueMicrotask(fn)` i `setTimeout(fn, 0)`. Ustaw je w kolejnosci wykonania i wyjasnij, dlaczego `process.nextTick` jest jedynym z tej trojki, ktory potrafi calkowicie ZABLOKOWAC pozostale dwa.
   - **Klucz:** Kolejnosc: `process.nextTick` -> `queueMicrotask` -> `setTimeout(fn, 0)`. `nextTick` ma w Node WLASNA kolejke, oddzielna od kolejki mikrozadan promise i oprozniana PRZED nia - zweryfikowane: rejestracja `Promise.resolve().then(...)` PRZED `process.nextTick(...)` daje mimo to wyjscie `nextTick -> then`, czyli kolejnosc w kodzie nie ma znaczenia. Blokowac potrafi tylko `nextTick`, bo jego kolejka oprozniana jest do konca po kazdej operacji, a callback moze dopisac do niej kolejny wpis - wiec rekurencyjny `process.nextTick` tworzy kolejke, ktora nigdy sie nie konczy, i event loop nie dostaje szansy przejsc do timerow ani do I/O (zweryfikowane: timer wszedl dopiero po 200000 obrotach). Dokumentacja Node nazywa to zaglodzeniem I/O i z tego powodu zaleca `setImmediate()` jako domyslny wybor.
3. Nocny skrypt konczy sie linia `process.exit(0)`. Co dzieje sie z zapytaniami HTTP, ktore w tym momencie sa jeszcze w locie, jaki kod wyjscia dostanie cron i dlaczego ten blad jest DROZSZY niz skrypt, ktory po prostu sie wywala? Podaj jedna linie naprawy bez usuwania `process.exit`.
   - **Klucz:** Zapytania w locie PRZEPADAJA bez sladu - `process.exit` nie czeka ani na mikrozadania, ani na timery, ani na otwarte gniazda; nie ma wyjatku, nie ma `unhandledRejection`, nie ma linii w logu. Cron dostaje kod wyjscia `0`, czyli SUKCES. Drozsze od wywalenia sie jest to dlatego, ze skrypt rzucajacy wyjatek konczy sie kodem `1` i trafia do monitoringu tej samej nocy, a ten konczy sie zielono i moze przezyc miesiace. Naprawa w jednej linii: `eksport().then(() => process.exit(0))` zamiast golego `process.exit(0)` na koncu pliku - albo, uczciwiej, USUNAC `process.exit`, bo Node sam konczy proces, gdy obie kolejki sa puste.

## Karta do powtorek (SM-2)

**Front:** W jakiej kolejnosci Node wykonuje kod - i gdzie w tej kolejnosci stoi `setTimeout(fn, 0)`?

**Back:** TRZY kolejki, kazda nastepna rusza dopiero gdy poprzednia jest PUSTA. (1) SYNCHRONICZNA: wszystkie zwykle linie, od gory do dolu, bez przerwy, az do konca pliku. (2) MIKROZADANIA: najpierw `process.nextTick` (osobna, wyzsza kolejka Node), potem `Promise.then`/`catch`/`finally`, `queueMicrotask` i WSZYSTKO po `await`; oprozniaja sie DO SUCHA, wiec mikrozadanie dopisane w trakcie tez zdazy w tym samym przebiegu. (3) MAKROZADANIA: `setTimeout`, `setInterval`, I/O, `setImmediate`. Wniosek: `setTimeout(fn, 0)` NIE znaczy "natychmiast", tylko "po wszystkich promisach" - przegrywa nawet z promisem zarejestrowanym nizej w pliku, a samo `0` jest zaciskane do min. 1 ms. `process.nextTick` wyprzedza mikrozadania promise nawet gdy stoi pod nimi, a rekurencyjny `nextTick` potrafi ZAGLODZIC timery i I/O. Cialo funkcji `async` wykonuje sie SYNCHRONICZNIE az do pierwszego `await` - `await` to nie pauza, tylko `return` z reszta ciala zapisana jako mikrozadanie, i kosztuje jeden obrot kolejki nawet na juz rozwiazanym promisie. Skutek: linia logu albo linia sprzatajaca postawiona POD wywolaniem asynchronicznym wykona sie PRZED jego zakonczeniem, wiec "gotowe" w logu znaczy tylko "doszedlem do tej linii". `process.exit(0)` nie czeka na nic z kolejek (2) i (3): kasuje je i konczy proces kodem `0`. `setTimeout(fn,0)` kontra `setImmediate(fn)` na gorze modulu ma kolejnosc NIEDETERMINISTYCZNA (dokumentacja Node), a wewnatrz callbacku I/O `setImmediate` jest zawsze pierwszy.

## Puenta

Pierwszy raz w tej serii bledna jest nie WARTOSC, tylko MOMENT. Kod liczy poprawnie - po prostu robi to pozniej, niz przeczytal to czlowiek. Ten log nie ma w sobie ani jednego falszywego zdania i mimo to wysyla diagnostyke w zla strone na cala noc, bo `[H] wyslane = 0` znaczy "doszedlem do tej linii", a czyta sie jako "nic nie poszlo". A jedna linia dopisana w dobrej wierze - `process.exit(0)`, zeby "skrypt konczyl sie czysto" - zamienia to w awarie idealna: zero wykonanej pracy, zero bledow i zielony status w cronie.
