# S67 — Cztery odpowiedzi z pieciu i zero dostepnosci rano

**Data:** 2026-09-05  
**Faza:** 1 — Alfabet czytania  
**Koncept:** Funkcje asynchroniczne - cztery kombinatory promisow (all / allSettled / race / any) i to, ze zaden z nich niczego nie anuluje  
**Format:** `what-if`  
**Motyw:** 🧭 Biuro wycieczek "Fjord Tours" w Reykjaviku - nocny agregator dostepnosci od czterech partnerow

## Koncept

Promise.all, allSettled, race i any uruchamiaja DOKLADNIE to samo i w tym samym momencie - roznia sie WYLACZNIE tym, co robia z PORAZKA: all odrzuca na pierwszym bledzie i GUBI wszystkie sukcesy, ktore juz przyszly; allSettled nie rzuca nigdy i oddaje komplet ze statusami; race oddaje pierwszy ROZSTRZYGNIETY wynik, wiec przy szybkim bledzie oddaje blad; any czeka na pierwszy SUKCES i rzuca dopiero przy komplecie porazek. A pod tym wszystkim lezy regula, ktorej nie widac w zadnej z tych czterech nazw: ZADEN z nich niczego NIE ANULUJE - kazde zapytanie, ktore juz wystartowalo, leci do konca ze wszystkimi skutkami ubocznymi, takze po tym, jak catch juz sie wykonal.

## Fabula

Biuro wycieczek "Fjord Tours" sprzedaje wyjazdy czterech partnerow: Golden Circle, Blue Lagoon, Glacier i Whale Watching. Nocny skrypt z crona pobiera od kazdego z nich dostepnosc na nastepny dzien i zapisuje ja do bazy.

W poniedzialek rano na stronie nie ma ANI JEDNEJ wolnej wycieczki. W logu jest jedna linia z bledem i jedno slowo: `przerwane`. Partner Blue faktycznie mial awarie i zwracal `503` — ale tylko on jeden.

Pytanie brzmi wiec nie "dlaczego Blue padl", tylko: co sie stalo z pozostalymi trzema, ktore odpowiedzialy poprawnie.

## Starcie 1 - laboratorium: cztery kombinatory na tych samych trzech zadaniach

```js
// STARCIE 1 - laboratorium: cztery sposoby na "zrob piec rzeczy naraz" (plik .js, node)
const ok  = (v, ms) => new Promise((r)   => setTimeout(() => r(v), ms));
const zle = (v, ms) => new Promise((_, j) => setTimeout(() => j(new Error(v)), ms));

async function main() {
  console.log("1) start");

  try {
    const r = await Promise.all([ok("A", 30), zle("B padl", 10), ok("C", 5)]);
    console.log("2) all ok:", r.join(","));
  } catch (e) { console.log("2) all catch:", e.message); }

  const s = await Promise.allSettled([ok("A", 30), zle("B padl", 10), ok("C", 5)]);
  console.log("3) allSettled statusy:", s.map((x) => x.status).join(","));
  console.log("4) allSettled tresc:", s.map((x) => x.status === "fulfilled" ? x.value : x.reason.message).join(" | "));

  try {
    const r = await Promise.race([ok("A", 30), zle("B padl", 10), ok("C", 5)]);
    console.log("5) race ok:", r);
  } catch (e) { console.log("5) race catch:", e.message); }

  try {
    const r = await Promise.race([ok("A", 30), zle("B padl", 1), ok("C", 5)]);
    console.log("6) race2 ok:", r);
  } catch (e) { console.log("6) race2 catch:", e.message); }

  try {
    const r = await Promise.any([zle("X padl", 5), ok("A", 30), zle("Y padl", 1)]);
    console.log("7) any:", r);
  } catch (e) { console.log("7) any catch:", e.name); }

  try {
    await Promise.any([zle("X padl", 5), zle("Y padl", 1)]);
  } catch (e) {
    console.log("8) any all-fail:", e.name, "| errors:", e.errors.map((x) => x.message).join(","));
  }

  const r2 = await Promise.all([ok("wolny", 30), ok("szybki", 1)]);
  console.log("9) all kolejnosc:", r2.join(","));

  const t1 = Date.now();
  await ok("a", 30); await ok("b", 30);
  const seq = Date.now() - t1;
  const t2 = Date.now();
  await Promise.all([ok("a", 30), ok("b", 30)]);
  const par = Date.now() - t2;
  console.log("10) sekwencyjnie >= 60 ms:", seq >= 60, "| rownolegle < 60 ms:", par < 60);

  console.log("11) koniec main");
}
main();
process.on("unhandledRejection", (e) => console.log("!! unhandledRejection:", e.message));
setTimeout(() => console.log("12) po 500 ms proces nadal zyje, zadnego unhandledRejection"), 500);
```

## Starcie 2 - "Fjord Tours": nocny agregator dostepnosci, jeden partner zwraca 503

```js
// STARCIE 2 - biuro wycieczek "Fjord Tours": nocny agregator dostepnosci (plik .js, node)
const zapisane = [];
const wywolania = [];

function pobierz(partner, ms, padnij = false) {
  wywolania.push(partner);
  return new Promise((ok, rej) => setTimeout(() => {
    if (padnij) return rej(new Error(partner + ": 503"));
    zapisane.push(partner);            // "zapis do bazy" dzieje sie TU, w srodku
    ok({ partner, miejsca: 4 });
  }, ms));
}

async function nocnySync() {
  console.log("[A] start, wywolania =", wywolania.length);
  try {
    const wynik = await Promise.all([
      pobierz("Golden", 20),
      pobierz("Blue", 40, true),       // ten jeden padnie
      pobierz("Glacier", 10),
      pobierz("Whale", 60),
    ]);
    console.log("[B] pobrano wszystko:", wynik.length);
    return "ok";
  } catch (e) {
    console.log("[C] blad synchronizacji:", e.message, "| zapisane =", zapisane.length);
    return "przerwane";
  }
}

nocnySync().then(async (r) => {
  console.log("[D] wynik funkcji:", r, "| zapisane =", zapisane.length);
  await new Promise((res) => setTimeout(res, 100));
  console.log("[E] po 100 ms: wywolania =", wywolania.length, "| zapisane =", zapisane.join(",") || "(puste)");
});

console.log("[F] koniec pliku, wywolania =", wywolania.length, "| zapisane =", zapisane.length);
```

## Quiz

1. **Piec zapytan do piec roznych API, jedno pada. Powiedz, co dokladnie dostaniesz z Promise.all i co z Promise.allSettled - a potem odpowiedz na pytanie, ktore rozstrzyga wybor: w ktorym z tych dwoch przypadkow BRAK jednej odpowiedzi powinien uniewaznic pozostale cztery, i podaj jeden konkretny przyklad z kazdej strony.**

   Promise.all odrzuca w chwili pierwszej porazki i oddaje JEDEN blad - cztery udane odpowiedzi przepadaja bezpowrotnie, a nawet drugi i trzeci blad zostana po cichu polkniete (zweryfikowane: przy dwoch odrzuceniach catch dostaje wylacznie szybsze, o drugim nie ma sladu ani w logu, ani w unhandledRejection). Promise.allSettled oddaje tablice czterech obiektow {status: 'fulfilled', value} / {status: 'rejected', reason} w kolejnosci WEJSCIA i nie rzuca nigdy. Rozstrzygajace pytanie: czy czesciowy wynik jest cos wart? Nie jest -> all: przelew zdejmujacy pieniadze z jednego konta i dopisujacy na drugie, albo zamowienie rezerwujace trzy rzeczy naraz - trzy z czterech to nie 75% sukcesu, tylko uszkodzony stan. Jest -> allSettled: dostepnosci od czterech niezaleznych partnerow, ceny z pieciu porownywarek, powiadomienia do listy adresatow - brak jednego nie uniewaznia pozostalych, a ich kasowanie jest czysta strata.

2. **Promise.race([zapytanie, timeout5s]) to najczestszy sposob na timeout w JS. Powiedz, co sie dzieje z zapytanie, gdy timeout wygra wyscig - i co sie dzieje z bledem zapytanie, jesli padnie ono sekunde PO tym, jak timeout juz oddal wynik. Osobno: czy ten timeout w ogole oszczedza cokolwiek po stronie serwera?**

   Gdy timeout wygra, zapytanie leci dalej, jakby nic sie nie stalo - race nie ma zadnego kanalu, ktorym moglby cokolwiek przerwac; jego wynik zostanie zignorowany, ale wszystkie skutki uboczne (zapis do bazy, pobranie pliku, obciazenie polaczenia) wykonaja sie w calosci. Jesli zapytanie padnie PO rozstrzygnieciu wyscigu, jego blad zostanie po cichu POLKNIETY: race ma podpiete handlery do wszystkich uczestnikow, wiec odrzucenie jest formalnie 'obsluzone' i nie wywola unhandledRejection ani zadnej linii w logu (zweryfikowane: po 300 ms zadnego ostrzezenia, podczas gdy promis odrzucony i nigdzie niepodpiety wywoluje je natychmiast). Odpowiedz na trzecie pytanie: NIE - taki timeout nie oszczedza po stronie serwera absolutnie niczego, oszczedza wylacznie czas uzytkownika po stronie klienta. Realne anulowanie wymaga AbortController i fetch(url, { signal }), czyli mechanizmu, ktory faktycznie zrywa polaczenie - a tego nie da sie udac promisem.

3. **Promise.any rzuca, gdy padna wszystkie zrodla. Powiedz, czym rozni sie ten wyjatek od zwyklego Error i co konkretnie zobaczy dyzurny w logu, jesli logger zapisuje e.message. Podaj jedna linie, ktora to naprawia. I na koniec trzy przypadki brzegowe: co zwraca Promise.all([]), co robi Promise.any([]), a co robi Promise.race([]).**

   Promise.any przy komplecie porazek rzuca AggregateError - bledy sa w tablicy e.errors (w kolejnosci WEJSCIA, nie padania: zweryfikowane, errors[0] to pierwszy element tablicy, chociaz padl jako ostatni), a e.message niesie tylko ogolne 'All promises were rejected'. Dyzurny, ktorego logger zapisuje e.message, zobaczy jedna bezuzyteczna linie i ANI JEDNEJ informacji o tym, ktore zrodlo padlo i dlaczego - te same puste rece co przy catch (e) { log(e.message) } na czyms, co nie jest Error (js-errors-10). Naprawa w jednej linii: log(e.errors ? e.errors.map(x => x.message).join(' | ') : e.message). Przypadki brzegowe, wszystkie zweryfikowane: Promise.all([]) zwraca [] natychmiast (i tak samo allSettled([])), Promise.any([]) rzuca AggregateError od razu z e.errors.length rownym 0, a Promise.race([]) NIGDY sie nie rozstrzyga - wisi w nieskonczonosc, nie rzucajac i nie zwracajac niczego (zweryfikowane wyscigiem z timerem: wygral timer). To ostatnie jest realnym bledem produkcyjnym: kod scigajacy liste zbudowana dynamicznie przy pustej liscie nie wywala sie ani nie loguje, tylko cicho zawisa - i wyglada dokladnie jak wolny serwer.

## Karta do powtorek (SM-2)

**Front:** Czym roznia sie `Promise.all`, `allSettled`, `race` i `any` — i co je wszystkie laczy?

**Back:** URUCHAMIAJA DOKLADNIE TO SAMO i w tym samym momencie; roznia sie WYLACZNIE stosunkiem do PORAZKI. `all` — odrzuca na PIERWSZYM bledzie i gubi wszystkie sukcesy, ktore juz przyszly (a kazdy kolejny blad polyka po cichu); wyniki w kolejnosci WEJSCIA, nie czasu. `allSettled` — NIGDY nie rzuca, oddaje komplet {status: 'fulfilled', value} / {status: 'rejected', reason}; cena: porazki musisz policzyc SAM, inaczej raportujesz 'ok' przy pustej odpowiedzi. `race` — pierwszy ROZSTRZYGNIETY, wiec przy szybkim bledzie oddaje BLAD. `any` — pierwszy SUKCES, bledy po drodze ignoruje; przy komplecie porazek rzuca AggregateError, ktorego e.message to bezuzyteczne 'All promises were rejected' — tresc siedzi w e.errors. Pytanie rozstrzygajace wybor: czy czesciowy wynik jest cos wart? Nie (przelew, rezerwacja) -> all. Tak (wachlarz niezaleznych integracji) -> allSettled. WSPOLNE I NAJWAZNIEJSZE: zaden z nich niczego NIE ANULUJE — zapytanie, ktore wystartowalo, leci do konca ze wszystkimi skutkami ubocznymi, takze PO wykonaniu catch (zweryfikowane: baza dostala trzeci zapis 20 ms po tym, jak funkcja zwrocila 'przerwane'). `race` jako timeout nie oszczedza po stronie serwera NICZEGO i po cichu polyka blad przegranego; realne anulowanie to AbortController + fetch(url, { signal }). Brzegowe: all([]) i allSettled([]) -> [] natychmiast, any([]) rzuca od razu z errors.length 0, a race([]) WISI NA ZAWSZE i wyglada jak wolny serwer. Koszt czasu: for...of z await sumuje czasy, Promise.all placi za najdluzszy.

## Puenta

To pierwszy dzien, w ktorym zle jest nie ZACHOWANIE kodu, tylko RAPORT o nim - i to raport falszywy w obie strony naraz. Funkcja mowi "przerwane", chociaz trzy czwarte pracy zostalo wykonane, a dane trzech partnerow lezaly w bazie jeszcze zanim log sie zapisal. Wczoraj (S66) klamala kolejnosc; dzis klamie SLOWO PORAZKA. W pracy AI Automation Engineera to jest codziennosc, nie ciekawostka: wachlarz integracji do systemu klienta zawsze ma jednego partnera, ktory akurat lezy, i cala roznica miedzy "system nie dziala" a "system dziala w 80%" mieszka w jednym slowie miedzy `Promise.` a `(`. Readiness bar Poziomu 1 brzmi doslownie "error handling, retries, rate limit + dedupe" - i wlasnie tutaj widac, dlaczego "error handling" nie znaczy "opakuj w try/catch": opakowany w try/catch kod z tego encountera wyglada wzorowo, loguje blad, nie wywala procesu, i produkuje zero dostepnosci przy trzech poprawnych odpowiedziach. Zdanie do zapamietania na rozmowe kwalifikacyjna: promis nie jest zadaniem, tylko powiadomieniem o zadaniu, ktore juz trwa - dlatego zaden kombinator niczego nie anuluje i kazdy timeout zbudowany na `race` chroni wylacznie cierpliwosc uzytkownika, nigdy serwera.
