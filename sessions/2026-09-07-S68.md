# S68 — Przycisk "Anuluj", ktory niczego nie anulowal (2026-09-07)

**Koncept:** Funkcje asynchroniczne — anulowanie: AbortController, signal i limit rownoleglosci

## Fabula
Biuro wycieczek "Fjord Tours" w Reykjaviku, dzien drugi. Wczoraj nocny agregator dostepnosci umarl na jednym partnerze i wyrzucil do smieci trzy poprawne odpowiedzi. Dzis do panelu doszedl przycisk "Anuluj" — recepcjonistka klika go, gdy klient rozmysli sie w polowie wyszukiwania. Przycisk dziala: spinner znika, interfejs wraca do formularza. Rachunek od dostawcy API na koniec miesiaca mowi jednak, ze zapytan bylo dokladnie tyle samo, co przed wdrozeniem przycisku.

## Zasada
`abort()` nie zatrzymuje ZADNEJ pracy — robi dokladnie dwie rzeczy: przestawia flage `signal.aborted` na `true` i emituje JEDNORAZOWE zdarzenie `abort`; kod, ktory tej flagi nie sprawdza i tego zdarzenia nie slucha, biegnie do konca jak gdyby nigdy nic, wiec jedyne, co da sie naprawde odwolac, to praca, ktora JESZCZE NIE RUSZYLA.

### Starcie 1 — laboratorium: jedno zadanie slucha sygnalu, drugie nie
```js
const ac = new AbortController();

function bezSygnalu(nazwa, ms) {
  return new Promise((res) => {
    setTimeout(() => { console.log(`  [praca] ${nazwa} SKONCZYL`); res(nazwa); }, ms);
  });
}

function zSygnalem(nazwa, ms, signal) {
  return new Promise((res, rej) => {
    const t = setTimeout(() => { console.log(`  [praca] ${nazwa} SKONCZYL`); res(nazwa); }, ms);
    signal.addEventListener('abort', () => {
      clearTimeout(t);
      rej(new Error(`${nazwa} przerwany`));
    });
  });
}

(async () => {
  console.log('aborted PRZED:', ac.signal.aborted);
  const a = bezSygnalu('A', 60);
  const b = zSygnalem('B', 60, ac.signal);
  setTimeout(() => { console.log('>>> ac.abort()'); ac.abort(); }, 20);

  const wyniki = await Promise.allSettled([a, b]);
  for (const w of wyniki) {
    console.log(w.status, '::', w.status === 'fulfilled' ? w.value : w.reason.message);
  }
  console.log('aborted PO:', ac.signal.aborted);
})();
```

### Starcie 2 — pula o limicie 2 na piec zadan, abort w polowie
```js
function pobierz(id, ms, signal) {
  if (signal.aborted) {
    console.log(`  POMINIETY ${id}`);
    return Promise.reject(new Error(`${id} pominiety`));
  }
  console.log(`  START ${id}`);
  return new Promise((res) => setTimeout(() => { console.log(`  KONIEC ${id}`); res(id); }, ms));
}

async function pula(ids, limit, fn) {
  const wyniki = [];
  let i = 0;
  const robotnicy = Array.from({ length: limit }, async () => {
    while (i < ids.length) {
      const moj = ids[i++];
      wyniki.push(await fn(moj).catch(() => "X:" + moj));
    }
  });
  await Promise.all(robotnicy);
  return wyniki;
}

(async () => {
  const ac = new AbortController();
  setTimeout(() => { console.log('>>> ac.abort()'); ac.abort(); }, 45);
  const w = await pula([1, 2, 3, 4, 5], 2, (id) => pobierz(id, 30, ac.signal));
  console.log('wyniki:', JSON.stringify(w));
})();
```

## Pytanie
Wypisz DOKLADNIE, linia po linii, output Starcia 1, a potem output Starcia 2. Przy Starciu 1 powiedz dodatkowo, ile pracy zostalo faktycznie wykonane PO wywolaniu `abort()`. Przy Starciu 2 wyjasnij dwie rzeczy: dlaczego `START 3` stoi POMIEDZY `KONIEC 1` a `KONIEC 2`, i dlaczego tablica `wyniki` nie jest w kolejnosci 1,2,3,4,5.

> Wskazowka kierunkowa, nie odpowiedz: `abort()` nie ma zadnej mocy nad `setTimeout`, ktory juz tyka — ma moc wylacznie tam, gdzie ktos go o zdanie PYTA. W Starciu 2 znajdz dokladnie tę jedną linię, w której pytanie w ogole pada, i sprawdz, kiedy robotnik do niej dochodzi.

## Klucz
Starcie 1: `abort()` po 20 ms odrzuca WYLACZNIE zadanie B, ktore zarejestrowalo listener na `abort` (i zdazylo zrobic `clearTimeout`). Zadanie A o kontrolerze nic nie wie, wiec jego timer 60 ms dochodzi do konca i drukuje `[praca] A SKONCZYL` JUZ PO abortcie — praca wykonana po anulowaniu to CALE zadanie A. `allSettled` czeka wiec do 60 ms i oddaje `fulfilled :: A` obok `rejected :: B przerwany`. Starcie 2: pula ma limit 2, wiec startuja 1 i 2. Gdy timer 1 sie odpala i drukuje `KONIEC 1`, jego promis rozwiazuje sie, a kontynuacja robotnika jest MIKROZADANIEM — a mikrozadania Node opróżnia POMIEDZY pojedynczymi callbackami timerow (regula z S66), wiec `START 3` wchodzi zanim odpali sie timer numeru 2. Stad `START 1, START 2, KONIEC 1, START 3, KONIEC 2, START 4`. Abort po 45 ms nie zatrzymuje ani 3, ani 4 — oba juz tykaja i drukuja swoje `KONIEC`. Dopiero gdy robotnik po `KONIEC 3` siega po piaty element i wywoluje `pobierz`, guard `if (signal.aborted)` pada i drukuje `POMINIETY 5`. Kolejnosc `wyniki` bierze sie z `push` PO `await`, czyli z kolejnosci ZAKONCZEN, a nie wejscia: `[1,2,3,"X:5",4]` — odrzucone piate wyladowalo przed czwartym, ktore w tym momencie jeszcze sie liczylo.

## Quiz
1. **Wywolujesz `fetch(url)` BEZ przekazania `{ signal }`, a potem `ac.abort()`. Co sie stanie z tym zapytaniem?**
   - Nic. `fetch` bez `signal` nie ma zadnego zwiazku z kontrolerem — `signal.aborted` przestawi sie na `true`, ale nikt tej flagi nie czyta, wiec zapytanie poleci do konca, serwer wykona swoja robote, a promis rozwiaze sie normalnie. Zweryfikowane na tej samej regule w Starciu 1: zadanie A bez sluchania sygnalu skonczylo sie po abortcie (`fulfilled :: A`).
2. **Wywolujesz `ac.abort()` trzy razy pod rzad, a potem dopisujesz nowy listener na `abort`. Ile razy odpali sie stary listener i czy odpali sie nowy?**
   - Stary odpali sie DOKLADNIE RAZ (zweryfikowane node v24.13.1: `listener wywolany razy: 1` po trzech `abort()`), bo zdarzenie `abort` emitowane jest jednorazowo. Nowy, dopisany JUZ PO abortcie, nie odpali sie WCALE — cisza. Stan da sie sprawdzic tylko flaga `signal.aborted` (`true`) albo `signal.reason` (gotowy `AbortError`). Praktyczny wniosek: kod, ktory rejestruje sluchacza za pozno, nie dowie sie o anulowaniu nigdy.
3. **Robisz `Promise.race([wolnaPraca, timeout])` i timeout wygrywa. Co dzieje sie z `wolnaPraca`?**
   - Leci dalej do samego konca ze wszystkimi skutkami ubocznymi — `race` nie anuluje przegranego, tylko przestaje sie nim interesowac. Zweryfikowane: po `race zwrocil: szybka` wolna praca i tak wydrukowala `wolna JEDNAK skonczyla`. Czyli timeout zbudowany na `race` kupuje wylacznie SZYBSZA ODPOWIEDZ, a nie mniejsze obciazenie — polaczenie, zapytanie do bazy i rachunek u dostawcy zostaja. Zeby faktycznie zwolnic zasob, trzeba przekazac `signal` do samej operacji.

## Karta do talii (SM-2)
- **Front:** Co dokladnie robi `controller.abort()`?
- **Back:** Nie zatrzymuje zadnej pracy. Ustawia `signal.aborted = true` i emituje JEDNORAZOWE zdarzenie `abort`. Zatrzymuje sie tylko ten kod, ktory sam sprawdza flage albo sluchal zdarzenia ZANIM padlo; reszta biegnie do konca. Realnie da sie odwolac wylacznie prace, ktora jeszcze nie ruszyla.

## Puenta
Wczoraj skonczylo sie na zdaniu "zaden kombinator niczego nie anuluje". Dzis okazuje sie, ze narzedzie stworzone WLASNIE do anulowania tez niczego nie anuluje — ono tylko oglasza. Roznica miedzy systemem, ktory ma anulowanie, a takim, ktory ma przycisk "Anuluj", to jest liczba miejsc, w ktore `signal` zostal FAKTYCZNIE przekazany. Na Poziomie 1 drabiny (error handling, retries, rate limit) to jest ta sama rodzina co 429 i backoff: klient placi za kazde zapytanie, ktore poleci, a nie za kazde, na ktore czeka.
