
# S70 — Reading errors: a `try/catch` ends where the function yields control (2026-09-09)

**Concept:** `try/catch` catches ONLY what throws in the same synchronous pass, before the function yields control. A promise without `await` and a `setTimeout` callback both throw *outside* the block and sail straight past it — the first as an `unhandledRejection`, the second as an `uncaughtException`.

**Scene:** 📦 Courier "Sendill", Reykjavík. The owner calls with something that sounds like a joke: *"the log says SENT for every parcel, and the carrier says half of them never arrived."* The night sender has a retry, a `try/catch` and a report. It has not reported a single error.

**Format:** BUG-HUNT

## Snippet 1 — the mechanics (note: not every numbered line will print)

```js
process.on("unhandledRejection", (e) => console.log("!! unhandledRejection:", e.message));
process.on("uncaughtException", (e) => console.log("!! uncaughtException:", e.message));

function A() { throw new Error("A: synchroniczny"); }
async function B() { throw new Error("B: asynchroniczny"); }

try { A(); } catch (e) { console.log("1)", e.name, "|", e.message); }

try { B(); } catch (e) { console.log("2) zlapane:", e.message); }
console.log("3) blok z B() przeszedl bez ani jednego catch");

function zFinally() {
  try { throw new Error("D: z try"); }
  catch (e) { return "z catch: " + e.message; }
  finally { console.log("4) finally leci zawsze"); }
}
console.log("5)", zFinally());

try {
  const dane = [{ id: 1 }, null];
  dane.map((x) => x.id);
} catch (e) {
  console.log("6)", e.name, "| instanceof TypeError:", e instanceof TypeError);
}

(async () => {
  try { await B(); } catch (e) { console.log("7) zlapane:", e.message); }

  try { setTimeout(() => { throw new Error("C: w timerze"); }, 0); }
  catch (e) { console.log("8) zlapane:", e.message); }
  console.log("9) blok z setTimeout tez przeszedl czysto");
})();
```

## Snippet 2 — the night label sender, with retry and a report

```js
async function wyslijDoPrzewoznika(id) {
  if (id % 2 === 0) throw new Error(`HTTP 429 dla paczki ${id}`);
  return `etykieta-${id}`;
}

async function zRetry(id, proby) {
  for (let i = 1; i <= proby; i++) {
    try {
      const wynik = wyslijDoPrzewoznika(id);
      console.log(`  [${id}] proba ${i} OK -> ${wynik}`);
      return wynik;
    } catch (e) {
      console.log(`  [${id}] proba ${i} padla: ${e.message}, ponawiam`);
    }
  }
  throw new Error(`${id}: wyczerpano ${proby} prob`);
}

(async () => {
  const raport = [];
  for (const id of [1, 2, 3]) {
    try {
      const w = await zRetry(id, 3);
      raport.push(`${id}: WYSLANE (${w})`);
    } catch (e) {
      raport.push(`${id}: BLAD (${e.message})`);
    }
  }
  console.log("RAPORT:", raport.join(" | "));

  const bezAwait = zRetry(4, 3);
  console.log("typ zwrotki:", typeof bezAwait, "| konstruktor:", bezAwait.constructor.name);
  bezAwait.catch((e) => console.log("dopiero .catch widzi:", e.message));
})();
```

```text
  A try/catch ENDS WHERE THE FUNCTION YIELDS CONTROL

  try {                          <-- the block lives for THIS pass only
     A();            throw ----> [CAUGHT]         same stack frame
     B();            (promise) ---- rejection arrives AFTER the block --X
     await B();      throw ----> [CAUGHT]         await pulls the rejection back in
     setTimeout(fn)  --------------- fn throws ms later, block long gone --X
  } catch (e) { ... }            <-- waits only for what falls NOW

  no await ==> you don't hold a result, you hold a PROMISE of one:
       `${promise}`  ->  "[object Promise]"
       if (promise)  ->  ALWAYS truthy, even with an error inside
```

**Question:** Print the exact output of Snippet 1 (the numbering has gaps — say which and why), then Snippet 2. Then name the ONE line in Snippet 2 that stops the retry from ever retrying, and explain why the log reports `OK` for a parcel that just failed — while the report for parcel 2 still ends in `BLAD`.

**The bug:** `const wynik = wyslijDoPrzewoznika(id);` — the missing `await`. Three consequences, each visible separately. (1) `wynik` is a PROMISE, not a label, so the template literal prints `[object Promise]` (it calls `String(x)`, and `Promise` has no meaningful `toString`; `if (promise)` is always truthy too). (2) `catch` never fires, because by the time the rejection lands, `zRetry` has long yielded control — so the loop runs exactly ONE iteration and returns on the first attempt; `proby` is a dead parameter and the `throw` after the loop is unreachable code. (3) The report still says `BLAD` for parcel 2, because `return wynik` hands back a rejected promise and the caller's `await zRetry(...)` unwraps it. The error didn't vanish: it moved one floor up and a few milliseconds later, losing the entire retry on the way and leaving a false `OK` in the log. Lines `2)` and `8)` in Snippet 1 are the same rule in the lab: `B()` without `await` rejects after the block is gone, and a `setTimeout` callback throws in a different stack frame — a `try` around `setTimeout` protects only the ACT OF SCHEDULING the timer, never its body.

## Quiz

1. `try { await Promise.all([a(), b()]); } catch (e) { ... }` — both `a()` and `b()` reject. How many errors does `catch` see, and what happens to the other one?
   **Key:** Exactly one — whichever rejected first. The second doesn't disappear; there is simply nobody left to receive it. `Promise.all` rejects once and drops the rest, and the orphaned rejection surfaces as an `unhandledRejection`. Only `Promise.allSettled` gives you the full picture.

2. A function reads `try { return "A"; } finally { return "B"; }`. What does it return, and why is that a trap when reading someone else's code?
   **Key:** `"B"`. A `return` in `finally` OVERRIDES both the `return` from `try` and any in-flight exception. It is the only place in JS where a cleanup block can silently swallow an error — every `return`/`throw` inside a `finally` is a red flag.

3. In `catch (e)` you write `if (e.message.includes("429")) retry();`. Give two reasons this can blow up or quietly do nothing.
   **Key:** (a) `e` need not be an `Error` — `throw "429"` gives `e.message === undefined`, so `.includes` throws a `TypeError` inside the `catch` itself. (b) The HTTP status usually isn't in the message text at all: `fetch` does not throw on 429 (you must read `response.status`), and axios keeps it in `e.response.status` — so a text match lets the rate limit through as "some other error".

## Card (SM-2)

**Front:** When will `try/catch` NOT catch an error from an async function?
**Back:** Whenever the `await` is missing. `try { asyncFn(); }` catches only what is thrown SYNCHRONOUSLY, before the function yields control; the rejection arrives later, outside the block, and ends as an `unhandledRejection`. Likewise a `try` around `setTimeout` protects only the scheduling of the timer, not its callback. Fix: `await` inside the `try`, or `.catch()` on the promise.

## Why this matters

The entry-level bar for this kind of role reads, literally, "error handling, retries, rate limits, dedupe". Today's snippet has all four words in the code and not one of them in the behaviour. The difference is a single missing `await` that no default linter flags and no happy-path test catches. Being able to spot that line in someone else's file is precisely what the job is paying for.
