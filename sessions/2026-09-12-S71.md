# S71 — Reading a diff: `return` inside a callback does not leave the function

**Concept:** `return` inside a `forEach` callback ends only that single callback run — it behaves like `continue`, and `forEach` throws the returned value away. So swapping `for...of` for `forEach` (or back) is never a style-only refactor when the loop body contains `return`, `break` or `continue`: it changes control flow.

**Story:** An accounting office in Reykjavík runs one n8n `Code` node that validates invoice batches coming from a webhook before they reach bookkeeping. On Friday a PR landed, described as *"style cleanup: loop to forEach, no logic changes"*. On Monday the bookkeeper calls: *"the log says the batch was rejected, and the invoices are in the system anyway."* The diff is one line removed, one line added.

## Where `return` ends

```txt
  BEFORE (for...of)                       AFTER (forEach)

  walidujPartie(...)                      walidujPartie(...)
  |- for (const item of items)            |- items.forEach( cb )
  |   |- item 1  -> push                  |   |- cb(item 1) -> push
  |   |- item 2  -> return ===+           |   |- cb(item 2) -> return ==+
  |   |- (item 3 UNREACHABLE) |           |   |     returns from cb ONLY <=+
  |- leaves the function <====+           |   |- cb(item 3) -> push  (keeps going!)
                                          |- console.log("przekazane: ...")
     return = LEAVES THE FUNCTION         |- return out   <- function ends HERE

                                             return in a cb = "continue" in disguise
                                             (and forEach discards its value)
```

## What the diff actually did

The PR changed logic, and it changed it inside the guard. `return` in a `forEach` callback returns from that one callback invocation, so `forEach` calls it for all three invoices — line `6)` proves it: the callback fires 3 times despite the `return`. Four consequences:

1. The guard became `continue`. The bad invoice is skipped; the batch keeps going.
2. The `[{ json: { status: "ODRZUCONA", ... } }]` object, which used to be the node's entire return value, is now the callback's return value — and `forEach` discards it (line `5)`: `forEach` returns `undefined`). The rejection status reaches nobody.
3. The `przekazane: N | suma: N` line used to be unreachable for a bad batch. Now it always prints, so the log holds two contradicting sentences side by side: `partia odrzucona na F-102` and `przekazane: 2`. That is the log the bookkeeper read, which is why her report sounds absurd.
4. `suma: 15500` is the sum of two invoices. The missing `98000` leaves no trace, because no one has anything to compare the total against.

Reading rule: whenever a diff swaps a `for` / `for...of` loop for an array method (or back), look for `return`, `break` and `continue` in the body. If any of them is there, it is not a style refactor — it is a control-flow change, whatever the PR description says.

## Quiz

1. You need to break out of a loop halfway and return a value from the function. Which of `forEach`, `for...of`, `some`, `every`, `map` can do that, and which cannot?
   *Key:* `for...of` (both `break` and `return` work), a classic `for`, and `some` / `every` (they stop at the first `true` / `false` — verified: `some` touched 2 of 3 elements). Not `forEach` (no way to break at all; `return` is `continue`, `break` is a syntax error) and not `map` (walks the whole array and returns a new one of the same length — `return` there is the element's value, not an exit).
2. A diff turns `- for (const x of lista) { await zapisz(x); }` into `+ lista.forEach(async (x) => { await zapisz(x); });` and the author writes "same thing, just parallel". What does the function really return, and what does its caller see?
   *Key:* It returns immediately, before anything has been saved. `forEach` does not care that the callback is `async`, does not await the promise and has nowhere to put it (verified: `zapisane = 0` at return time, `3` after 50 ms). An error thrown in such a callback has nowhere to land and ends up as an `unhandledRejection`. Correct: `for...of` with `await` (sequential) or `await Promise.all(lista.map(async ...))` — `map`, not `forEach`, because only `map` hands back the array of promises.
3. You are reading a PR described as "refactor, no logic changes". Name two line shapes in the diff that are red flags under that description.
   *Key:* (1) `return` / `break` / `continue` in a body that the diff moves between a loop and a callback — control-flow keywords inside a line that was supposedly "just moved". (2) An operator swap that looks cosmetic but covers a different input set: `||` to `??`, `==` to `===`, `>` to `>=`, `let` to `const` inside a loop. Both are caught by the same question: not "what changed in the text" but "which input value now behaves differently".

## Spaced-repetition card

**Front:** What does `return` do inside a `forEach` callback?

**Back:** It ends only that one callback run (it behaves like `continue`), and `forEach` discards its value — `forEach` always returns `undefined` and cannot be broken out of. The function containing the `forEach` keeps going. That is why swapping `for...of` for `forEach` in a diff is never a style refactor when the body contains `return`, `break` or `continue`. To break: `for...of`, `some`, `every`.

## Why it matters

The single most repeated requirement on this career track is n8n, and a large part of working in n8n is reading someone else's `Code` node and deciding whether a PR labelled "cleanup" can be merged. This diff is two lines, passes every linter and every happy-path test — and turns a validating node into a filtering one. Being able to say "this is not a refactor" is exactly the skill the phase boss tests.
