# S76 - `await` inside `forEach` returns empty data before anything happened

**Concept:** an `await` inside a `forEach` callback suspends only that callback, not the loop. `forEach` discards every value the callback returns - and an `async` callback returns a Promise - so the loop finishes immediately and the function returns before the first `await` has settled.

**Story.** A car-parts wholesaler in Reykjavik has an n8n workflow: web form -> webhook -> `Code` node that queries three suppliers -> Merge -> comparison email. The owner reports three separate things. (1) The email says "0 offers found", yet clicking "Execute Node" in the n8n panel shows the offers. (2) The error counter is always `0`, even though one supplier's API has been dead for a week. (3) Occasionally, on a manual run, the email is correct - and nobody can say what was different about that run.

**Format:** order-of-execution / predict-output.

## Round 2 - the same `Code` node, one loop apart

```js
const DOSTAWCY = {
  1: { nazwa: "Bilastodin", ms: 30 },
  2: { nazwa: "Vefur",      ms: 10 },
  3: { nazwa: "Nordur",     ms: 0  }
};

function pobierzCene(id) {
  const d = DOSTAWCY[id];
  return new Promise((resolve, reject) => {
    setTimeout(() => {
      if (!d) return reject(new Error("brak dostawcy " + id));
      resolve({ dostawca: d.nazwa, cena: id * 1000 });
    }, d ? d.ms : 5);
  });
}

// VERSION A - straight out of the prompt
async function zbierzOferty(items) {
  const wyniki = [];
  let bledy = 0;

  items.forEach(async (item) => {
    try {
      const oferta = await pobierzCene(item.json.dostawcaId);
      wyniki.push(oferta);
    } catch (e) {
      bledy++;
    }
  });

  console.log('A-log) wyniki.length =', wyniki.length, '| bledy =', bledy);
  setTimeout(() => console.log('A-po-100ms) wyniki.length =', wyniki.length, '| bledy =', bledy), 100);
  return [{ json: { ofert: wyniki.length, bledy, najtanszy: wyniki[0] ?? null } }];
}

// VERSION B - same function, one loop changed
async function zbierzOfertyB(items) {
  const wyniki = [];
  let bledy = 0;

  for (const item of items) {
    try {
      const oferta = await pobierzCene(item.json.dostawcaId);
      wyniki.push(oferta);
    } catch (e) {
      bledy++;
    }
  }

  console.log('B-log) wyniki.length =', wyniki.length, '| bledy =', bledy);
  return [{ json: { ofert: wyniki.length, bledy, najtanszy: wyniki[0] ?? null } }];
}

const items = [
  { json: { dostawcaId: 1 } },
  { json: { dostawcaId: 2 } },
  { json: { dostawcaId: 99 } },
  { json: { dostawcaId: 3 } }
];

(async () => {
  console.log('A)', JSON.stringify(await zbierzOferty(items)));
  await new Promise(r => setTimeout(r, 200));
  console.log('B)', JSON.stringify(await zbierzOfertyB(items)));
})();
```

## Answers to the three complaints

1. **"0 offers" while the panel shows offers.** `forEach` does not wait. The `await` suspends only its own callback; the loop finishes in the same tick and `return` runs with an empty array. The n8n preview shows the state *after* everything settled - exactly the `A-po-100ms)` line.
2. **Error counter stuck at 0.** Same cause, not a different one: `bledy++` runs in a `catch` five milliseconds later. Note how dangerous the pair is - `ofert: 0, bledy: 0` reads as "I checked and there is nothing" and actually means "I never got to ask". From the data this function returns, those two are indistinguishable.
3. **Occasionally correct.** Nothing in the code differs. Something else just happened to yield control for long enough between the `forEach` and the read. A race is not "sometimes broken" - it is always broken and sometimes invisible, which is why re-running it is not a debugging strategy.

Two more: the rejected promise for `id: 99` does **not** produce an `unhandledRejection`, because the `try/catch` with the `await` sits *inside* the callback. Remove the `try/catch` and `forEach` has nobody to hand the rejected promise to, so Node reports it - the unhandled version is the louder one. And `najtanszy` is `wyniki[0]`, i.e. the first element of the array: in B the first one *ordered*, in A the first one that *answered* (Nordur, the most expensive of the three). There is not a single price comparison anywhere in the code.

Fix is one line, but you have to pick which: `for...of` + `await` (ordered, sequential, time = sum of latencies), or `await Promise.allSettled(items.map(...))` (parallel, time = slowest). `Promise.all` is out - one dead supplier rejects the whole thing and throws away the successes that already arrived.

## Quiz

1. Four ways to run async work over a list (`forEach(async)`, `for...of` + `await`, `Promise.all(map)`, `for await...of`). Build a table: does the caller wait / do they run in parallel / what does one failure do. Which one for a `Code` node querying three suppliers, and why reject the other three?
   **Key:** `allSettled` - it waits, runs in parallel (time = slowest, not sum) and returns a full `{status, value|reason}` set, so a dead supplier is *countable* and does not take the other two down. `forEach` does not wait; `for...of` loses on latency at five suppliers; `Promise.all` is wrong because a supplier failing is a *normal* state here, not an exception - and that is the entire criterion between `all` and `allSettled`.

2. Order of six things scheduled at the same moment: sync code, `process.nextTick`, `Promise.then`, `queueMicrotask`, `setTimeout(fn, 0)`, `setImmediate`. Which pair has no guaranteed order at module top level? What does `await null` actually do?
   **Key:** measured: `sync, nextTick, promise, queueMicrotask, setImmediate, setTimeout0`. Guaranteed: all sync code first; then the separate, higher `process.nextTick` queue; then microtasks in scheduling order; then macrotasks. **Not** guaranteed: `setTimeout(fn, 0)` vs `setImmediate` scheduled at module top level - it depends on how long process startup took. Six consecutive runs here all put `setImmediate` first, which is reproducible and still no guarantee on another machine. `await null` waits on no work at all: it wraps `null` in a resolved promise and yields for the rest of the tick, which is why line `3)` still sees `0` - you do not need a network or a timer to lose the race.

3. Version A has no syntax error and its `return` is honest: at the moment it returns, `wyniki` really is empty. Design the boundary so that "zero offers because of a timing bug" cannot silently become an email saying "we found 0 offers". What goes in the log and the metric, and which single assertion would have caught this on day one?
   **Key:** return `{ probowano, udane, bledy, czasMs }` and open with `if (probowano !== items.length) throw new Error(...)` - in version A that fires immediately, because `probowano` is `0` against `items.length === 4`. It works because it asks for something the current contract does not carry: how many attempts were *made*, not how many results *remain*. Logs: A -> `code.niekompletny probowano=0 oczekiwano=4 czasMs=0` (zero milliseconds for four HTTP calls is an alarm by itself); B -> `code.ok probowano=4 udane=3 bledy=1 czasMs=~45 dostawca_bledny=99`. Metric: a histogram of `czasMs` plus the counter `probowano - (udane + bledy)`, which should be permanently zero.

## Spaced-repetition card

**Front:** What does `await` do inside `items.forEach(async (i) => { await f(i); ... })`, and what does the code below the loop see?

**Back:** It suspends only that one callback, not the loop. `forEach` discards every value the callback returns - and an `async` callback returns a Promise - so the loop has nothing to wait on, finishes immediately, and the code below sees the state from before any work happened (empty array, counter at `0`). This is not "sometimes broken": it is always broken, just sometimes invisible. Waiting variants: `for...of` + `await` (sequential, order preserved) or `Promise.allSettled(items.map(f))` (parallel, one failure does not take the rest; `Promise.all` rejects everything).

## Takeaway

The function has a `try/catch`, an error counter, a `najtanszy` field and returns well-formed JSON - and it had made exactly zero requests at the moment it reported its result. The difference between someone who "knows n8n" and someone who gets paid for it runs right through here: the first reads the code and sees that everything is there; the second reads the code and asks *when* everything will be there.
