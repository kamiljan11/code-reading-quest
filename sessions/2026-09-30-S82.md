# S82 - Comparison operators: everything from the network and from .env is a string

**Concept:** an HTTP header, a value read from `.env` and a status code relayed by a proxy all arrive as strings, and a comparison operator never asks where a value came from - only what TYPE it is. Two strings are compared character by character (`"120" <= "60"` is `true`), a string against a number is converted to numbers (`2 < "3"` works), `undefined` against anything is `false` in both directions, and `===` converts nothing (`"429" === 429` is `false`).

**Story:** a campervan rental in Selfoss pulls bookings from four partners over REST. Partners rate-limit and answer `429` with a `Retry-After` header. The client has two functions: the retry decision and the pagination loop. Config lives in `.env`. The owner asks why one partner banned their API key while another partner's bookings quietly went missing.

## Round 1 - the retry decision (5 responses, 5 decisions)

```js
// Klient REST API partnera "Husbill": decyzja o ponowieniu po bledzie.
// konf przychodzi z pliku .env, wiec kazda wartosc jest STRINGIEM.
const konf = { maxProb: "3", maxCzekaj: "60" };
const log = [];

function czyPonowic(res, proba) {
  const ra = res.headers["retry-after"];   // naglowek HTTP = zawsze string
  const limitOk = proba < konf.maxProb;
  const krotko = ra <= konf.maxCzekaj;
  log.push(res.status + "@" + proba);
  return res.status === 429 && limitOk && krotko || res.status >= 500 && limitOk;
}

const A = czyPonowic({ status: 429,   headers: { "retry-after": "120" } }, 1);
const B = czyPonowic({ status: 429,   headers: { "retry-after": "9" } },   1);
const C = czyPonowic({ status: 503,   headers: {} },                       2);
const D = czyPonowic({ status: "429", headers: { "retry-after": "30" } },  1);
const E = czyPonowic({ status: 502,   headers: {} },                       3);

console.log("1)", A, B, C, D, E);
console.log("2)", "120" <= "60", "9" <= "60", 120 <= "60");
console.log("3)", undefined <= "60", undefined > "60");
console.log("4)", 3 < "3", 2 < "10", "2" < "10");
console.log("5)", log.join(" "));
```

## Round 2 - one pagination loop, four partners, three "is there a next page" checks

```js
// Synchronizacja rezerwacji z czterech partnerow. Kazdy ma 2 strony danych,
// ale kazdy inaczej oznacza "to byla ostatnia strona".
const partnerzy = {
  Node:   { s1: { dane: 2, next: "s2" }, s2: { dane: 3, next: null } },
  PHP:    { s1: { dane: 2, next: "s2" }, s2: { dane: 3, next: "" } },
  Python: { s1: { dane: 2, next: "s2" }, s2: { dane: 3, next: "None" } }, // str(None)
  Brak:   { s1: { dane: 2, next: "s2" }, s2: { dane: 3 } },                 // pole pominiete
};

function synchronizuj(strony, dalej) {
  let kursor = "s1", zapytan = 0, rekordy = 0;
  do {
    const s = strony[kursor] ?? { dane: 0, next: kursor }; // nieznany kursor = pusta strona
    rekordy += s.dane;
    kursor = s.next;
    zapytan++;
  } while (dalej(kursor) && zapytan < 5);                   // bezpiecznik: max 5 zapytan
  return zapytan;
}

const warunki = {
  "W1 k":          k => k,
  "W2 k !== null": k => k !== null,
  "W3 k != null":  k => k != null,
};

let i = 6;
for (const [nazwa, w] of Object.entries(warunki)) {
  const wynik = Object.keys(partnerzy).map(p => synchronizuj(partnerzy[p], w));
  console.log(`${i++})`, nazwa.padEnd(14), wynik.join(" "));
}
console.log("9)", Boolean("None"), "" != null, undefined !== null);
```

## Verified

Run with `node v22.22.2` and re-checked on `node v24.13.1` before the answer key was written.

```
1) true false true false false
2) true false false
3) false false
4) false true false
5) 429@1 429@1 503@2 429@1 502@3
6) W1 k           2 2 5 2
7) W2 k !== null  2 5 5 5
8) W3 k != null   2 5 5 2
9) true true true
```

Diagnosis: three of the five decisions are wrong. A retries although the server asked for 120 s against a 60 s limit (`"120" <= "60"` is `true` - two strings compared character by character), which is how you get your key banned. B gives up on a 9 s wait (`"9" <= "60"` is `false`, because `"9" > "6"`), which is how a booking goes missing. D gives up because the status arrived as text (`"429" === 429` is `false`, and `"429" >= 500` is numerically `false` too). C and E are correct (`2 < "3"` converts to numbers). Fix: `Number(...)` on the header, the config and the status, once, at the boundary. In Round 2 no check is right for all four partners - `5` means the safety cap fired. One normalisation line fixes all three: `kursor = (s.next === undefined || s.next === "" || s.next === "None") ? null : s.next;` after which every check prints `2 2 2 2` (verified).

## Quiz

1. Line 3 shows `undefined <= "60"` and `undefined > "60"` are both `false`. What does that mean for any `ra <= limit` decision when the server sends no header at all, and how do you write a default wait that does not overwrite a real `"0"`?
   **Key:** a missing header always lands in the `false` branch whichever way the comparison is written, so the author decides, not the server. Use `Number(res.headers["retry-after"] ?? "1")` - `??` before converting, because `Number("0") || 1` turns a genuine zero into `1`.
2. One partner ends the list with an empty string, another with `"None"`. Where should "this is the last page" be decided: in the loop condition, or in one place right after the response arrives?
   **Key:** in one place at the boundary (normalise the cursor to `null`). The loop condition stays simple (`k !== null`) and each new partner costs one line of normalisation instead of a new special case in the loop.
3. Without the `zapytan < 5` cap, how many requests would the Python partner get under W1, and what does the provider see? What is missing so that the cap firing is not a silent failure?
   **Key:** unbounded - a flood of requests with the same cursor; the provider answers `429` or revokes the key. The cap turns an infinite loop into a quiet bug (5 requests, 2 real pages), so it needs a log line or alert when it fires.

## Card

**Front:** `Retry-After: "120"` and a `.env` limit of `"60"` - what does `ra <= limit` return, and how do you fix it?
**Back:** `true`, because JS compares two strings character by character (`"1" < "6"`). Everything from the network and from `.env` is text - convert to numbers once, at the boundary (`Number(...)`), before comparing anything. Number vs string converts to numbers (`2 < "3"` works), `undefined` vs anything is `false` both ways, and `===` converts nothing (`"429" === 429` is `false`).

## Takeaway

A retrying API client is the first thing an automation engineer writes for a client and the last thing anyone checks, because it works in the demo. Here the same operator retried too early once (ban) and not at all once (lost booking), both because nobody turned text into a number at the boundary. "What do you do with a 429?" comes up in every technical interview for integration roles.
