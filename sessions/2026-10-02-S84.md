# S84 - Reading errors: what survives when you log an error as JSON

**Concept:** `message`, `stack` and `cause` on an `Error` are own but NON-ENUMERABLE properties, so `JSON.stringify(err)` and spread `{ ...err }` do not see them. What reaches the log is `{}`, or only the fields someone assigned by hand in the constructor (`status`, and even `name` if it was set with `this.name = ...`). On top of that, when every promise passed to `Promise.any` rejects, it throws an `AggregateError` with the generic message "All promises were rejected"; the real causes live in `e.errors`, in INPUT order, not in the order they failed.

**Story:** a museum in Reykjavik runs a chat guide. Each visitor question goes to three indexes at once (vectors, BM25, cache) and the first answer wins. On Saturday all three failed. The client reported "the guide is silent", and the on-call engineer opened the n8n log: two entries with `"blad":{}`, one with only a `status`, and one fully readable entry - the one where somebody had thrown a plain string. Why does the log describe properly only the failure that was written worst?

## Round 1 - a custom error class and `Promise.any` over three indexes

```js
// Wyszukiwarka RAG przewodnika muzealnego "Safnid" w Reykjaviku.
// Pytanie idzie do trzech indeksow naraz; bierzemy pierwszy, ktory odpowie.
class BladIndeksu extends Error {
  constructor(indeks, status) {
    super(`indeks ${indeks} odpowiedzial ${status}`);
    this.indeks = indeks;
    this.status = status;
  }
}

const szukaj = (indeks, status, ms) =>
  new Promise((ok, nie) => setTimeout(() =>
    status === 200 ? ok(`${indeks}: 3 fragmenty`) : nie(new BladIndeksu(indeks, status)), ms));

async function main() {
  const e1 = new BladIndeksu("wektory", 503);
  console.log("1)", e1.name, e1 instanceof Error, e1.message);
  console.log("2)", JSON.stringify(e1));
  console.log("3)", JSON.stringify({ blad: e1.message, ...e1 }));
  console.log("4)", String(e1));

  try {
    await Promise.any([szukaj("wektory", 503, 10), szukaj("bm25", 429, 20), szukaj("cache", 404, 5)]);
  } catch (e) {
    console.log("5)", e.name, "|", e.message);
    console.log("6)", e.errors.map((x) => x.status).join(","), e.errors.length);
  }

  const wynik = await Promise.any([szukaj("wektory", 503, 10), szukaj("bm25", 200, 30), szukaj("cache", 200, 50)]);
  console.log("7)", wynik);
}
main();
```

## Round 2 - same outage, one layer up: a logger that writes every error as JSON

```js
// Ten sam pipeline, warstwa logow: kazdy blad laduje jako JSON w logu (n8n / observability).
class BladIndeksu extends Error {
  constructor(indeks, status) {
    super(`indeks ${indeks} odpowiedzial ${status}`);
    this.name = "BladIndeksu";
    this.status = status;
  }
}

function logA(etap, e) {            // wersja z produkcji
  return JSON.stringify({ etap, blad: e });
}
function logB(etap, e) {            // propozycja z code review
  return JSON.stringify({
    etap,
    typ: e?.name ?? typeof e,
    msg: e?.message ?? String(e),
    przyczyna: e?.cause?.message ?? null,
  });
}

const zdarzenia = [
  ["embed", new TypeError("Cannot read properties of undefined (reading 'embedding')")],
  ["szukaj", new BladIndeksu("wektory", 503)],
  ["rerank", new Error("rerank padl", { cause: new BladIndeksu("bm25", 429) })],
  ["prompt", "limit tokenow przekroczony"],
];

let n = 8;
for (const [etap, e] of zdarzenia) {
  console.log(`${n++})`, logA(etap, e), "||", logB(etap, e));
}
```

## Verified

Run with `node v22.22.0` and re-checked on `node v24.13.1` before the answer key was written.

```
1) Error true indeks wektory odpowiedzial 503
2) {"indeks":"wektory","status":503}
3) {"blad":"indeks wektory odpowiedzial 503","indeks":"wektory","status":503}
4) Error: indeks wektory odpowiedzial 503
5) AggregateError | All promises were rejected
6) 503,429,404 3
7) bm25: 3 fragmenty
8) {"etap":"embed","blad":{}} || {"etap":"embed","typ":"TypeError","msg":"Cannot read properties of undefined (reading 'embedding')","przyczyna":null}
9) {"etap":"szukaj","blad":{"name":"BladIndeksu","status":503}} || {"etap":"szukaj","typ":"BladIndeksu","msg":"indeks wektory odpowiedzial 503","przyczyna":null}
10) {"etap":"rerank","blad":{}} || {"etap":"rerank","typ":"Error","msg":"rerank padl","przyczyna":"indeks bm25 odpowiedzial 429"}
11) {"etap":"prompt","blad":"limit tokenow przekroczony"} || {"etap":"prompt","typ":"string","msg":"limit tokenow przekroczony","przyczyna":null}
```

Diagnosis: (a) `JSON.stringify` and spread take only own ENUMERABLE properties. In line 9 `name` and `status` were assigned in the constructor, so they are enumerable and survive; the `TypeError` in line 8 has no such field, and in line 10 the real cause (a 429 from BM25) sits in the non-enumerable `cause`, so both log `{}`. The only complete entry is line 11, because a thrown string is not an object. The worst practice produces the best log entry - which means the logger is at fault, not the errors. Line 1: without `this.name = ...` the name comes from the prototype (`"Error"`). (b) `AggregateError.message` is always generic; the causes are in `e.errors`, in input order (`503,429,404`) even though `cache` failed first after 5 ms. Log `e.errors.map(x => ({ index: x.indeks, status: x.status, msg: x.message }))`, and serialize errors through explicitly chosen fields (like `logB`), never through `JSON.stringify(err)`.

## Quiz

1. `console.log(e1)` prints the message and the stack, while `JSON.stringify(e1)` gives `{"indeks":"wektory","status":503}`. Why the difference for the same object?
   **Key:** Node's `console.log` uses `util.inspect`, which deliberately shows the stack and non-enumerable error fields. `JSON.stringify` takes only own enumerable properties, and `message`/`stack` are not enumerable.
2. The class in Round 1 never sets `this.name`. What does `e1.name` print, and what should be added so the class name shows up in logs and in `stack`?
   **Key:** `"Error"`, inherited from `Error.prototype`. Add `this.name = "BladIndeksu"` (or `new.target.name`) after `super(...)`. V8 builds the first line of `stack` lazily, so `stack` then also starts with `BladIndeksu:` (checked).
3. `Promise.any` failed on all three indexes. How do you build one log line that shows all three causes, and why is `e.message` not enough?
   **Key:** log `e.errors.map(x => x.indeks + ":" + x.status)` or the messages. `e.message` is the fixed text "All promises were rejected" and contains none of the causes.

## Card

**Front:** What does `JSON.stringify(new Error("index failed"))` print, and why?
**Back:** `{}`. `message`, `stack` and `cause` are own but non-enumerable, and `JSON.stringify` (and spread) only take own enumerable properties. Only hand-assigned fields survive (`this.status`, `this.name`). Log errors through chosen fields: `{ name: e.name, message: e.message, cause: e.cause?.message }`. `AggregateError` keeps the real causes in `e.errors`.

## Takeaway

In a RAG system an outage usually looks like silence: the assistant goes quiet and the log says `{}`. The observability part of every integration role boils down to one question: can you tell from the log WHICH index failed and with WHAT status? A logger built on `JSON.stringify(err)` has nothing to say at the first serious outage.
