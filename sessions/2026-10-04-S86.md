# S86 - Objects: object keys are exact strings, HTTP headers are not

**Concept:** a plain object compares keys character by character, so `"Content-Type"` and `"content-type"` are TWO different keys, and spread or `Object.fromEntries` only overwrite an identical key. HTTP header names are case-insensitive: the `Headers` class lowercases every name and, when a name repeats, JOINS the values with `", "` (`Set-Cookie` is kept separately in `getSetCookie()`). Headers kept in a plain object either duplicate or lose values, depending on who reads them later.

**Story:** a car rental company in Keflavik pulls availability from a partner's REST API. Since yesterday the partner answers 401 to every other request, and after each 429 the client hits the API again one second later. The day before, an AI assistant sent a PR titled "shared header helper, logic unchanged". The on-call engineer swears the API key is correct.

## Round 1 - the same headers in a plain object and in `Headers`

```js
// Klient REST wypozyczalni samochodow "Bilaleiga" w Keflaviku: naglowki odpowiedzi od partnera.
// Partner zwraca naglowki jako liste par [nazwa, wartosc] (tak jak surowe HTTP).
const surowe = [
  ["Content-Type", "application/json"],
  ["X-Request-Id", "r-81"],
  ["content-type", "text/html"],
  ["Set-Cookie", "sesja=a1"],
  ["set-cookie", "region=is"],
];

const obj = Object.fromEntries(surowe);
console.log("1)", Object.keys(obj).length, obj["content-type"]);
console.log("2)", obj["Content-Type"], obj["X-REQUEST-ID"]);

const h = new Headers(surowe);
console.log("3)", h.get("CONTENT-TYPE"));
console.log("4)", h.get("set-cookie"), "|", h.getSetCookie().length);
console.log("5)", [...h.keys()].join(","));
```

## Round 2 - the AI PR: "shared header helper, logic unchanged"

```js
// PR od asystenta AI: "wspolny helper do naglowkow, logika bez zmian".
const DOMYSLNE = { "Content-Type": "application/json", Authorization: "Bearer KLUCZ-A" };

function zbudujNaglowki(wlasne) {
  return { ...DOMYSLNE, ...wlasne };
}

const n1 = zbudujNaglowki({ "content-type": "text/csv", authorization: "Bearer KLUCZ-B" });
console.log("6)", Object.keys(n1).length);

const h1 = new Headers(n1);
console.log("7)", h1.get("authorization"));
console.log("8)", h1.get("content-type"));

// Odpowiedz 429 po zmapowaniu przez SDK partnera na zwykly obiekt:
const odp = { status: 429, headers: { "Retry-After": "30" } };
const czekaj = Number(odp.headers["retry-after"]) || 1;
console.log("9)", czekaj);

const odp2 = new Headers(odp.headers);
console.log("10)", Number(odp2.get("retry-after")) || 1);
```

## Verified

Run with `node v22.22.0` and re-checked with `node v24.21.0` on the local machine before the answer key was written.

```
1) 5 text/html
2) application/json undefined
3) application/json, text/html
4) sesja=a1, region=is | 2
5) content-type,set-cookie,set-cookie,x-request-id
6) 4
7) Bearer KLUCZ-A, Bearer KLUCZ-B
8) application/json, text/csv
9) 1
10) 30
```

Diagnosis: (a) spread only overwrites an identical key string, so `"Authorization"` and `"authorization"` (and both `Content-Type` variants) all survive; `Headers`, and therefore `fetch`, lowercases the names and joins the values, so the partner receives `Bearer KLUCZ-A, Bearer KLUCZ-B` and answers 401. The PR description is false. Fix: build headers with `new Headers(DEFAULTS)` and call `h.set(name, value)` for every custom one, because `set` replaces instead of appending. (b) In the plain object the key is `"Retry-After"`, but the code reads `"retry-after"`: `undefined` -> `Number(undefined)` is `NaN` -> `NaN || 1` is `1`. Fix: read through `Headers.get` (line 10 gives 30) or lowercase the keys when mapping the response.

## Quiz

1. Why does `h.get("CONTENT-TYPE")` find a value while `obj["X-REQUEST-ID"]` gives `undefined`?
   **Key:** `Headers` lowercases names on write and on read, so case does not matter. A plain object compares the key as an exact string, and `"X-REQUEST-ID"` is a different string from `"X-Request-Id"`.
2. What is the difference between `h.set("authorization", x)` and `h.append("authorization", x)` on a `Headers` object that already has `Authorization`?
   **Key:** `set` replaces the value (one remains), `append` adds another one and `get` returns both joined by `", "`. Spreading plain objects with different letter case behaves like `append` once it passes through `Headers`.
3. Why does `Set-Cookie` get its own `getSetCookie()` method when other repeated headers can be joined with a comma?
   **Key:** a cookie value can itself contain a comma (for example a date in `Expires`), so a `", "` join cannot be split back reliably. `getSetCookie()` returns an array of separate values.

## Card

**Front:** What does `fetch` send if you build headers as `{ ...{ Authorization: "Bearer A" }, ...{ authorization: "Bearer B" } }`?
**Back:** Both. Spread only overwrites an IDENTICAL key string, so the object has two keys, and `Headers` lowercases them to `authorization` and joins them: `Bearer A, Bearer B`. HTTP headers ignore case, plain objects do not. Build them with `new Headers()` and `set()`, read them with `get()`.

## Takeaway

Integration work is rarely about the `fetch` call itself; it is about the seams, such as who reads the headers and how. Seeing headers stored in a plain object and asking about letter case right away saves a team an afternoon of 401s with a "but the key is correct" ticket.
