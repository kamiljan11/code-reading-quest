# S89 - Reading errors: a fallback that never ran, and a model that got `undefined` as context

**Concept:** `try/catch` inside an async function only catches what rejects before the function hands control back. `return embed(q)` returns the promise without waiting, so its rejection flies past `catch` to the caller; `return await embed(q)` waits inside `try` and `catch` works. The second argument of `.then(ok, onErr)` only handles a rejection of the PREVIOUS step, never an error thrown inside `ok`. A `.catch(fn)` that returns nothing hands `undefined` on as a SUCCESS, so the next `.then` carries on with an empty context.

**Story:** a library in Isafjordur runs RAG over its catalogue: the query is embedded through an external API, matching chunks are glued into a context and sent to a model. An AI assistant opened a PR titled "simplified error handling, logic unchanged". Since then an empty query never falls back, and once in a while the model answers a question with no context at all, and nothing in the logs says why.

## Round 1 - two search variants after the PR

```js
// Biblioteka "Bokasafn" w Isafjordur: RAG nad katalogiem; embedding przez zewnetrzne API.
// PR od asystenta AI: "uproszczony error handling, logika bez zmian".
const embed = async (q) => {
  if (!q.trim()) throw new Error("pusty prompt");
  return [0.12, 0.87];
};

async function szukajA(q) {
  try {
    return embed(q); // PR: usuniete "await", "bo i tak od razu zwracamy"
  } catch (e) {
    return "fallback-A";
  }
}

async function szukajB(q) {
  try {
    return await embed(q);
  } catch (e) {
    return "fallback-B";
  }
}

szukajA("   ").then((w) => console.log("1)", w), (e) => console.log("2)", e.message));
szukajB("   ").then((w) => console.log("3)", w));
szukajB("sagi").then((w) => console.log("4)", w.length));
console.log("5) wyslano trzy zapytania");
```

## Round 2 - gluing the context from chunks (separate file)

```js
// Ten sam PR: sklejanie kontekstu z chunkow przed wyslaniem do modelu.
const kontekst = (chunki) => {
  if (chunki.length === 0) throw new Error("brak chunkow");
  return chunki.join(" | ");
};
const szukaj = (q) =>
  Promise.resolve(q === "saga" ? ["Egils saga", "Njals saga"] : []);

szukaj("mapa")
  .then(kontekst, (e) => "BRAK KONTEKSTU (siec)")
  .then((k) => console.log("6)", k))
  .catch((e) => console.log("7)", e.message));

szukaj("mapa")
  .then(kontekst)
  .catch((e) => console.log("8) log:", e.message))
  .then((k) => console.log("9) do modelu:", k));

szukaj("saga")
  .then(kontekst)
  .then((k) => console.log("10)", k))
  .finally(() => console.log("11) koniec"));
```

**Question:** put the output of both rounds in order (each round runs as its own file). Which numbers never appear? Then, as a reviewer: (a) why did fallback-A never run, even though it sits in `catch`; (b) why did the model receive `undefined` as context, and which single change stops it.

## Verified

Run with `node v22.22.0` and re-checked with `node v24.21.0` on the local machine before the answer key was written.

```
5) wyslano trzy zapytania
3) fallback-B
4) 2
2) pusty prompt
```

```
8) log: brak chunkow
10) Egils saga | Njals saga
7) brak chunkow
9) do modelu: undefined
11) koniec
```

Lines `1)` and `6)` never appear. Diagnosis: (a) `return embed(q)` without `await` returns the promise before it rejects, so the `catch` in `szukajA` has nothing to catch and the error goes to the caller; it even arrives AFTER the results of `szukajB`, because returning a promise from an async function costs extra microtask ticks. Fix: `return await embed(q)`. (b) the `.catch` logs and returns nothing, so the chain goes back to the success track with `undefined` and the next `.then` sends it to the model. Fix: rethrow in `catch` (`throw e`), or return an explicit fallback and check it before calling the model. `.then(kontekst, onErr)` never sees the error thrown by `kontekst` (line 6 is silent, line 7 catches it).

## Quiz

1. When does `return await p` inside `try` differ from `return p`?
   **Key:** only when `p` rejects: with `await` the rejection comes back into `try` and `catch` handles it; without it the promise leaves the function and the error lands at the caller.
2. What does the second argument of `.then(ok, onErr)` catch?
   **Key:** only a rejection of the promise `.then` is called on. An error thrown inside `ok` itself goes on to the next `.catch`.
3. What does the next `.then` receive after `.catch(e => console.log(e))`?
   **Key:** `undefined` as an ordinary success, because the catch callback returned nothing. To stop the chain, rethrow or return an explicit value and check it.

## Card

**Front:** An async function has `try { return fetchX(); } catch { return "fallback"; }`. What happens when `fetchX` rejects?
**Back:** `catch` does NOT run: the promise leaves `try` unsettled and the rejection reaches the caller. Write `return await fetchX();`.

## Takeaway

In production, RAG rarely breaks in the search itself; it breaks in the error handling around it: a fallback that never runs and a model that gets an empty context without a single alarm. Asking at every `return` inside `try` whether it awaits, and at every `catch` what it returns, catches this in review.
