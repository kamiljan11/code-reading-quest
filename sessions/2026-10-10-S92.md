# S92 - Objects: porting a Python dict to a JS object, and the 9 o'clock slot that merged two partners

**Concept:** a plain JS object key is always a string, and integer-like keys come out in ascending order before all other keys. So porting a Python dict merges `9` and `"9"` into one key, changes the key order, and makes `JSON.stringify` an unreliable "did it change?" check: equal for hour keys in any order, different for word keys in a different order. On top of that `==` compares references, spread copies shallowly like `dict.copy()`, and `undefined` (the port of `None`) disappears from JSON.

**Story:** a geothermal bathhouse by Myvatn counted guests per entry hour from two booking partners with a Python script and compared the schedule with yesterday's every morning. An AI assistant ported the script to an n8n `Code` node: "ported 1:1 from Python (dict -> object), logic unchanged". On day one the 9:00 slot showed 5 guests against a cloakroom limit of 4, and the change check kept flipping between "no change" and "changed" although nobody touched anything. (Pure node simulation; partner B sends the hour as text.)

## Round 1 - the entry counter after the port

```js
// Laznie "Jardbodin" przy Myvatn: licznik osob na godziny wejscia.
// PR od asystenta AI: "przepisane 1:1 z Pythona (dict -> obiekt), logika bez zmian".
// Oryginal (Python):
//   licznik = {}
//   for r in rezerwacje:
//       licznik[r["godz"]] = licznik.get(r["godz"], 0) + r["osoby"]
const rezerwacje = [
  { godz: 18, osoby: 2 },
  { godz: 9, osoby: 4 },
  { godz: "9", osoby: 1 }, // partner B wysyla godzine jako tekst
  { godz: 18, osoby: 3 },
];

const licznik = {};
for (const r of rezerwacje) {
  licznik[r.godz] = (licznik[r.godz] ?? 0) + r.osoby;
}

console.log("1)", licznik);
console.log("2)", Object.keys(licznik), Object.keys(licznik).includes(9));
console.log("3)", licznik[9] === licznik["9"], 9 in licznik);
console.log("4)", JSON.stringify(licznik));
```

## Round 2 - schedule change check and schedule copy (separate file)

// Starcie 2 — osobny plik: "czy grafik sie zmienil?" i kopia grafiku.
// W Pythonie: wczoraj == dzis porownuje TRESC, grafik.copy() to plytka kopia.
const wczoraj = { 18: 5, 9: 5 };

console.log("5)", wczoraj == dzis, JSON.stringify(wczoraj) === JSON.stringify(dzis));

kopia.pon.sloty.push(21);

console.log("7)", grafik.pon.sloty, "wt" in grafik);

## Verified

Run with `node v22.22.0` and re-checked with `node v24.21.0` on the local machine before the answer key was written. The Python original prints `{18: 5, 9: 4, '9': 1}`, and `{18: 5, 9: 5} == {9: 5, 18: 5}` is `True` (python3 3.13).

```
1) { '9': 5, '18': 5 }
2) [ '9', '18' ] false
3) true true
4) {"9":5,"18":5}
```

```
5) false true
6) false
7) [ 9, 18, 21 ] false
8) 2 {"otwarte":false} true
```

Diagnosis: (a) partner B's `"9"` merges with `9` into one key (Python kept `'9': 1` separate, here 5 guests at 9:00); key order becomes 9, 18 instead of insertion order 18, 9; `powod: undefined` vanishes from JSON (Python `None` -> `null`) and a missing field gives `undefined` instead of `KeyError`. Also `{ ...grafik }` shares the `sloty` array just like `copy()`. (b) hour keys are integer-like, so both objects serialize identically (`true`), while `sauna`/`basen` keep insertion order, so the same schedule serializes differently (`false`); `==` never looks at content at all. (c) `const licznik = new Map();` keyed by `Number(r.godz)`, or an explicit `String(r.godz)` after validation if 9 and "9" really are the same hour: that has to be a decision, not an accident.

## Quiz

1. What does `const o = {}; o[9] = 1; o["9"] += 1; console.log(o)` print?
   **Key:** `{ '9': 2 }`. A plain object key is a string, so `9` and `"9"` are the same slot.
2. In what order does `Object.keys` return the keys of `{ b: 1, 20: 1, a: 1, 3: 1 }`?
   **Key:** `['3', '20', 'b', 'a']`: integer-like keys ascending first, then string keys in insertion order.
3. Why is `JSON.stringify(a) === JSON.stringify(b)` not a reliable "same content" test?
   **Key:** the result depends on the order of string keys and `undefined` disappears; compare by sorted keys or with a deep-equal function.

## Card

**Front:** Port from Python: `licznik[r.godz]` in JS, when one partner sends `9` and the other `"9"`. How many keys, and of what type?
**Back:** One key `'9'` (a string), and the values add up. Python would keep two keys. In JS use a `Map` or normalize the key type before writing.

## Takeaway

For an integrator, Python work often means moving a script into an n8n `Code` node. Asking about key type, key order and copies at every `dict -> {}` keeps you from shipping a schedule on which two bookings from two systems became one.
