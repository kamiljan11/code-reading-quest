# S100 - Reading errors: a `catch` block is code too, and it can throw

**Concept:** `throw` in JS accepts any value: an `Error`, a custom class with a `response` field, a string, even `null`. A `catch` handler that assumes the shape of an HTTP error (`e.response.status`) throws a TypeError of its own when it receives a network error, a thrown string or `null`, and that new error replaces the original one in the log. On top of that, a single `try` wrapped around the whole loop ends the batch at the first failure, so the remaining items never get a single attempt.

**Story:** a building-supplies wholesaler in Akureyri sends orders to a carrier's API every night. An n8n `Code` node takes a batch of orders, calls the endpoint for each one and logs the status or the error. The carrier fails in different ways: a 422 with a reason, a dropped connection (`socket hang up`), and its old SDK sometimes throws a bare `"timeout"` string or `null`. An AI assistant opened a PR: "unified error handling: one try for the whole batch, no logic change". Since then the log has almost no network errors but plenty of TypeErrors, and the warehouse wants to know why half the orders never shipped when "there was only one error". (Pure node simulation; `wyslij` plays the carrier.)

## Round 1 - per-order error handler (predict the output)

```js
// Hurtownia budowlana "Byko-Nord" w Akureyri: node Code w n8n wysyla zamowienia do API przewoznika.
class HttpError extends Error {
  constructor(status, data) {
    super("Request failed with status code " + status);
    this.name = "HttpError";
    this.response = { status, data };
  }
}
function wyslij(id) {
  if (id === "Z1") return { ok: true };
  if (id === "Z2") throw new HttpError(422, { blad: "brak kodu pocztowego" });
  if (id === "Z3") throw new Error("socket hang up");
  if (id === "Z4") throw "timeout";
  if (id === "Z5") throw null;
}
const opisz = (e) => `${e.response.status}: ${e.response.data.blad}`;
["Z1", "Z2", "Z3", "Z4", "Z5"].forEach((id, i) => {
  try {
    wyslij(id);
    console.log(`${i + 1})`, id, "ok");
  } catch (e) {
    try { console.log(`${i + 1})`, id, opisz(e)); }
    catch (e2) { console.log(`${i + 1})`, id, "catch padl:", e2.message, "| oryginal:", `${e}`, e instanceof Error); }
  }
});
```

## Round 2 - the "one try for the whole batch" PR (separate file)

```js
// Starcie 2 - osobny plik: PR od asystenta AI "ujednolicona obsluga bledow: jeden try na cala partie, logika bez zmian".
class HttpError extends Error {
  constructor(status, data) {
    super("Request failed with status code " + status);
    this.name = "HttpError";
    this.response = { status, data };
  }
}
let proby = 0;
function wyslij(id) {
  proby++;
  if (id === "Z1") return { ok: true };
  if (id === "Z2") throw new HttpError(422, { blad: "brak kodu pocztowego" });
  if (id === "Z3") throw new Error("socket hang up");
  if (id === "Z4") throw "timeout";
  if (id === "Z5") throw null;
}
function przed(ids) {
  const out = [];
  for (const id of ids) {
    try { wyslij(id); out.push(id + ":ok"); }
    catch (e) { out.push(id + ":" + (e?.response?.status ?? String(e))); }
  }
  return out.join(" ");
}
function po(ids) {
  const out = [];
  try {
    for (const id of ids) { wyslij(id); out.push(id + ":ok"); }
  } catch (e) {
    out.push("blad " + e.response.status + " " + e.message);
  }
  return out.join(" ");
}
console.log("6)", przed(["Z1", "Z2", "Z3", "Z4", "Z5"]));
proby = 0;
console.log("7)", po(["Z1", "Z2", "Z3"]));
try { console.log(po(["Z1", "Z3", "Z2"])); } catch (e) { console.log("8)", e.name, e.message); }
try { console.log(po(["Z5", "Z1"])); } catch (e) { console.log("9)", e.name, e.message); }
console.log("10)", proby, "z 8");
```

## Verified

Run as separate files on node v22.22.0 and v24.21.0 before writing the key, 10/10 lines identical. The fix from the diagnosis was run separately.

```
1) Z1 ok
2) Z2 422: brak kodu pocztowego
3) Z3 catch padl: Cannot read properties of undefined (reading 'status') | oryginal: Error: socket hang up true
4) Z4 catch padl: Cannot read properties of undefined (reading 'status') | oryginal: timeout false
5) Z5 catch padl: Cannot read properties of null (reading 'response') | oryginal: null false
```

```
6) Z1:ok Z2:422 Z3:Error: socket hang up Z4:timeout Z5:null
7) Z1:ok blad 422 Request failed with status code 422
8) TypeError Cannot read properties of undefined (reading 'status')
9) TypeError Cannot read properties of null (reading 'response')
10) 5 z 8
```

Diagnosis: lines 3-5: the handler assumes every error has `response`. A network error does not, neither does the string `"timeout"` (reading a property of a string gives `undefined`), and nothing can be read from `null`. Round 1 only shows this because the handler is wrapped in a second `try`; in a plain node without it the TypeError would escape `catch` and kill the execution. Line 6: the pre-PR version read fields through `?.` and `??`, so every order got its own entry with the original error. Line 7: after the PR the first failure (422 on Z2) ends the loop, Z3 is never sent, and the log has one error entry for three orders. Lines 8-9: for an error without `response`, the `catch` in `po` throws and the function returns a TypeError instead of a result; `socket hang up` and `null` are lost. Line 10: 5 calls for 8 orders across three batches. Smallest fix: move the `try` back inside the loop and use a handler that does not assume a shape: `e?.response ? status + reason : e instanceof Error ? e.message : "nie-Error: " + String(e)` (verified separately: `Z1:ok | Z3:socket hang up | Z2:422: brak kodu pocztowego | Z4:nie-Error: timeout | Z5:nie-Error: null`).

## Quiz

1. A `catch` contains `log(e.response.status)` and receives a network error with no `response`. What ends up in the log? (Key: `TypeError: Cannot read properties of undefined (reading 'status')`, thrown from the `catch`; the original network error is lost.)
2. What are `message` and `instanceof Error` after `throw "timeout"`? (Key: `e.message` is `undefined` and `e instanceof Error` is `false`; it is a plain string with no stack and no fields.)
3. How does a `try` around the whole loop differ from a `try` inside the loop for a batch of orders? (Key: around the loop, the first failure ends the whole batch and the rest get no attempt. Inside, a failure affects one order and the loop continues.)

## Card

**Front:** A `catch` using `e.response.status` receives a network error (no `response`). What do you see in the log?
**Back:** A TypeError from the `catch` (`Cannot read properties of undefined (reading 'status')`), not the original error. The handler should read through `?.` and tell `instanceof Error` apart from non-Error values.

## Takeaway

In automation work an n8n `Code` node sits between two APIs, and those APIs fail in more ways than `e.response.status` assumes. Reading `catch` as ordinary code that can throw too, and counting how many items in a batch actually got an attempt, is the difference between "the network dropped once" and "half the orders silently never shipped".
