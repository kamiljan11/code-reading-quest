# S111 - Reading a diff: a "shorter retry" in a REST API client

**Concept:** read a diff line by line and ask "what did this line do BEFORE and what does it do AFTER", feeding the same data to both versions. A "shorter" retry loop can change behaviour in three places at once: an idempotency key moved into the loop is new on every attempt (the partner stores a duplicate), a loop starting at `0` with `<= MAX` makes one extra attempt, and `status === 429 || 500` is always truthy, so everything is retried, including `400`. Small changes next to it matter too: `!res.ok` is not the same as `status >= 400`.

**Story:** an e-bike rental in Isafjordur, Iceland, books bikes with a partner through the partner's REST API. The partner's gateway is sometimes overloaded and returns `503` even though the booking was already stored, so the client retries with the same `Idempotency-Key` and the partner recognises the repeat. An AI assistant opened a PR "shorter retry, key generated per request, no logic change" and "simplified" response handling along the way. A week later: tourists with two bookings for the same bike, the partner complaining about bursts of `400`s, the availability cache failing on every `304`, and an invoice for two days plus a helmet fee of 4 500 500 ISK.

## Round 1 - the same function before and after the PR, three partner scenarios (what if + predict the output)

```js
// Klient API partnera rezerwacji: wypozyczalnia e-rowerow "Rafhjol" w Isafjordur.
// Partner (symulacja) ZAPISUJE rezerwacje takze wtedy, gdy bramka odda 503 (timeout po zapisie).
// Dedupe po stronie partnera: po naglowku Idempotency-Key (tu pole `klucz`).
const MAX = 3;
let licznik = 0;
const nowyKlucz = () => `rez-${++licznik}`;

function zrobPartnera(statusy) {
  const zapisane = new Map();
  let n = 0;
  return {
    zapisane,
    get zadan() { return n; },
    wyslij(req) {
      const status = statusy[n++] ?? 201;
      if (status !== 400 && !zapisane.has(req.klucz)) zapisane.set(req.klucz, req.rower);
      return status;
    },
  };
}

// PRZED PR
function rezerwujPrzed(api, rower) {
  const klucz = nowyKlucz();
  for (let proba = 1; proba <= MAX; proba++) {
    const status = api.wyslij({ klucz, rower });
    if (status === 201) return `OK po ${proba}`;
    if (!(status === 429 || status >= 500)) return `BLAD ${status}`;
  }
  return "PORAZKA";
}

// PO PR od asystenta AI: "krotszy retry, klucz generowany przy zadaniu, logika bez zmian"
function rezerwujPo(api, rower) {
  for (let proba = 0; proba <= MAX; proba++) {
    const status = api.wyslij({ klucz: nowyKlucz(), rower });
    if (status === 201) return `OK po ${proba}`;
    if (!(status === 429 || 500)) return `BLAD ${status}`;
  }
  return "PORAZKA";
}

const scenariusze = { A: [503, 201], B: [400, 400, 400, 400, 400], C: [503, 503, 503, 503] };
let nr = 1;
for (const [nazwa, statusy] of Object.entries(scenariusze)) {
  for (const [wersja, fn] of [["przed", rezerwujPrzed], ["po", rezerwujPo]]) {
    const api = zrobPartnera(statusy);
    const wynik = fn(api, "R7");
    console.log(`${nr++})`, nazwa, wersja, wynik, "| zadan:", api.zadan, "| rezerwacji u partnera:", api.zapisane.size);
  }
}
```

## Round 2 - five small changes from the same PR in response handling (separate file)

```js
// Starcie 2 - osobny plik: piec malych zmian z tego samego PR w obsludze odpowiedzi partnera.
const odp304 = { status: 304, ok: false, body: "" };
const odp200 = { status: 200, ok: true, body: '{"wolne":0,"cena":"4500"}' };

// PRZED: if (res.status >= 400) -> BLAD     PO: if (!res.ok) -> BLAD
const sprawdzPrzed = (res) => (res.status >= 400 ? "BLAD" : "OK");
const sprawdzPo = (res) => (!res.ok ? "BLAD" : "OK");
console.log("7)", sprawdzPrzed(odp304), sprawdzPo(odp304));

// PRZED: dane.wolne ?? "brak danych"        PO: dane.wolne || "brak danych"
const dane = JSON.parse(odp200.body);
console.log("8)", dane.wolne ?? "brak danych", dane.wolne || "brak danych");

// PRZED: Number(dane.cena) * 2 i Number(dane.cena) + 500     PO: dane.cena * 2 i dane.cena + 500
console.log("9)", Number(dane.cena) * 2, dane.cena * 2, Number(dane.cena) + 500, dane.cena + 500);

// PRZED: body: JSON.stringify(zapytanie)    PO: body: zapytanie (fetch zamienia body na tekst przez String)
const zapytanie = { rower: "R7", dni: 2 };
console.log("10)", String(JSON.stringify(zapytanie)), String(zapytanie));

// PRZED: `${BAZA}/rowery/${encodeURIComponent(id)}`    PO: `${BAZA}/rowery/${id}`
const BAZA = "https://api.partner.is/v1";
const id = "R7/serwis?full=1";
console.log("11)", `${BAZA}/rowery/${encodeURIComponent(id)}`);
console.log("12)", `${BAZA}/rowery/${id}`);
```

## Verified

Run with node v22.23.4 and v24.21.0, each round as a separate file, before the key was written.

```
1) A przed OK po 2 | zadan: 2 | rezerwacji u partnera: 1
2) A po OK po 1 | zadan: 2 | rezerwacji u partnera: 2
3) B przed BLAD 400 | zadan: 1 | rezerwacji u partnera: 0
4) B po PORAZKA | zadan: 4 | rezerwacji u partnera: 0
5) C przed PORAZKA | zadan: 3 | rezerwacji u partnera: 1
6) C po PORAZKA | zadan: 4 | rezerwacji u partnera: 4
```

```
7) OK BLAD
8) 0 brak danych
9) 9000 9000 5000 4500500
10) {"rower":"R7","dni":2} [object Object]
11) https://api.partner.is/v1/rowery/R7%2Fserwis%3Ffull%3D1
12) https://api.partner.is/v1/rowery/R7/serwis?full=1
```

Diagnosis: before the PR the key is created once, before the loop, so the second attempt carries `rez-1` and the partner treats it as a repeat (line 1: one booking). After the PR `nowyKlucz()` sits inside the loop, so a `503` that was stored plus a `201` become two bookings of the same bike (line 2). The loop now starts at `0`, which shifts the attempt counter in the log (`OK po 1` after two requests) and, with `<= MAX`, adds a fourth attempt (lines 4 and 6). `(status === 429 || 500)` evaluates to `500` for a `400`, which is truthy, so the early `BLAD` return never happens and bad input is retried until `PORAZKA` (line 4). Scenario C shows that even the old version reports `PORAZKA` while the partner holds a booking: after the last attempt the client should ask the partner for the state by key instead of reporting failure. In Round 2 only `"4500" * 2` is safe: `!res.ok` flags a `304` as an error, `||` turns `0` free bikes into "no data", `"4500" + 500` concatenates, a body without `JSON.stringify` is sent as `[object Object]`, and an id without `encodeURIComponent` rewrites the path and query (lines 11 and 12).

Fix: the version before the PR (key before the loop, attempts from 1, `status === 429 || status >= 500`), plus `status >= 400`, `??`, `Number()`, `JSON.stringify` and `encodeURIComponent` in response handling.

## Quiz

1. Why must the `Idempotency-Key` be generated ONCE, before the retry loop, and not on every call inside it? (Key: the key identifies the OPERATION, not the request. Every attempt of the same booking must carry the same key so the partner can recognise a repeat after a timeout; a new key per attempt is a new booking for the partner.)
2. What does `status === 429 || 500` return for `status = 400`, and how do you write "retry only 429 and 5xx"? (Key: `false || 500` returns `500`, which is truthy, so the condition is always true. Correct: `status === 429 || status >= 500`.)
3. A diff changes `if (res.status >= 400)` to `if (!res.ok)`. For which statuses is the result different? (Key: 1xx and 3xx, e.g. `304 Not Modified`: `res.ok` is true only for 200-299.)

## Card

**Front:** `for (let p = 1; p <= 3; p++) send({ key: newKey(), data })` - what is wrong with this retry?
**Back:** The idempotency key is created on every attempt, so the partner sees each repeat as a NEW operation and stores a duplicate after a timeout. Generate the key once, before the loop, and send the same one on every attempt.

## Takeaway

REST APIs and webhooks are the second most common requirement in the AI integration job ads this log tracks, and in practice that means retries, idempotency and status handling, exactly where an AI-generated PR will always be "shorter". Whoever feeds the same data to BEFORE and AFTER for every line of the diff stops it before a tourist gets a bike booked for someone else.
